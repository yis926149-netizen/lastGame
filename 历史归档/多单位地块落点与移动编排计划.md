## 一、背景与目标

当前单位移动的现状：

- 每个地块默认只有 **一个中心落点**（`RealCenterWorldCoordinate`）。
- 单位从当前地块中心，用 `Vector3.MoveTowards` 逐帧直线走到下一个地块中心。
- 地块占用是**单单位模型**：一个地块只能有一个单位（`GetUnit()` / `SetHaveUnit(bool, GameObject)`）。
- 寻路（Dijkstra）把「当前站着单位的格子」当作不可通行（攻击目标格例外）。

由此产生的问题：

1. 多个单位走同一条路时，视觉上会完全重叠、穿模。
2. 一个地块无法自然地容纳多个单位并列站立。
3. 移动轨迹过于机械、标准（所有单位都贴格心走折线）。

目标（分两层，互不冲突）：

- **逻辑层**：单位仍然按地块路径行进、占用、判定。
- **表现层**：每个地块提供多个落点（槽位），单位按「前—现—后」路径关系选择合适的落点，移动时逐点走落点，实现并列与自然感。

### 现有代码核对结论

本计划以下内容已与当前实现逐项对照，后文以代码实际语义为准：

- `UnitMovementSystem.CanEnterCell` 当前检查的是 `movementCost`、迷雾和 `HaveUnit/GetUnit`，普通路径不能经过任何 `HaveUnit` 格；不是独立的“站立单位集合”判断。
- `HexCellData` 同时存在三套占用概念：旧的 `HaveUnit/GetUnit`、单主体的 `Occupant/GetOccupant`、近战临时使用的 6 个 `AttackerSlots`。多单位改造不能把它们直接合并成一个列表。
- 当前 `_reservedDestinations` 只预留最终目的地，不预留中间路径节点；同时它还被卡牌部署、AI 部署和兵营出生点检查使用，因此升级时必须提供格级和槽位级两种查询。
- `UnitBrainBase` 会缓存逻辑路径并逐格调用 `MoveTo`，而 `UnitMovementSystem` 的一次移动任务目前只包含这一段路径。整条路径槽位预留与现有逐格决策模式存在接口冲突，必须在阶段 1 先定型。
- 当前地图生成阶段没有统一可查询的“山地模型、资源模型、公共建筑、宝箱装饰”碰撞体。槽位烘焙应使用生成期障碍代理，不能直接假设运行时模型已经存在。
- 当前 `SeedService` 没有“地图种子 + 地块坐标 + 槽位索引”的哈希接口；该接口属于本方案必须新增的基础设施。

## 二、核心概念：逻辑路径 与 视觉路径 分离

这是整套系统的基础。

### 逻辑路径（保持不变）

```text
[A, B, C, D]   // 地块坐标序列，来自 Dijkstra 最短路
```

用途：

- 寻路与最短代价；
- 地块占用、到达判定；
- 战斗、采集、阵营、规则判定。

### 视觉路径（新增）

```text
[A.slot_x, B.slot_y, C.slot_z, D.slot_w]   // 每个地块内部的具体落点
```

用途：

- `transform.position` 的实际移动目标；
- 单位在地块内的站位表现；
- 移动过程中的并列与避让。

改造后，`UnitMovementSystem.UpdateMovement` 的移动目标从：

```text
cell.RealCenterWorldCoordinate
```

变为：

```text
cell 的某个落点（slot）的世界坐标
```

`MoveTowards` 本身**不需要改**，仍保持匀速直线插值。

## 三、落点 / 槽位系统设计

### 3.0 三类位置状态必须分离

本方案中的“槽位”只表示普通站立和移动表现，不替代现有所有占用状态：

```text
StandingSlot：单位当前站在该格的普通站位槽
ReservedSlot：移动任务预留但尚未到达的站位槽
AttackerSlot：近战攻击方向临时槽，独立于普通站位槽
```

约束：

- `StandingSlot` 与 `ReservedSlot` 共享同一组有效槽位，但同一 `(cell, slotId)` 不能被两个单位同时持有。
- `AttackerSlot` 仍然按进入方向管理，最多 6 个，不能计入普通站位容量，除非后续玩法明确要求攻击者占用普通站位。
- `Occupant` 不再表示“格上唯一单位”。实施时应删除其业务依赖，或暂时保留为兼容字段并明确其语义为“逻辑格主人”，不能用于枚举格内单位。
- `GetUnit()` 不能继续作为多单位场景的完整查询接口。应新增统一的 `GetStandingUnits()`、`GetUnitsByFaction()` 或等价 API，并逐步迁移旧调用方。

### 3.1 每个地块拥有多个落点

每个地块（`HexCellData` 或独立组件）持有多个单位落点，例如：

```text
        slot0
  slot1  center  slot2
        slot3
```

**已定方案：5 个锚点 = 四角 + 中心。**

```text
左前、右前、左后、右后、中心
```

其中 `中心` 锚点固定为 0 偏移、**不参与抖动**（见 3.1.1 约束二），因此 4.2 的「起点从 0 平滑过渡」始终有一个真中心可用。所有四角锚点都必须落在偏移带（地块最小尺寸的 25% ~ 40%）内——不设「上缘 / 下缘」这类贴边落点，它们会把单位推到超过地块半径的位置，与偏移上限直接冲突。

“四角”不是六边形的天然顶点，必须定义为相对于世界 XZ 轴的四个内部锚点，而不是六边形边界上的四个顶点。实施前固定以下参数定义：

- `cellWidth` 使用 `2 * InnerRadius`；`cellDepth` 使用 `1.5 * OuterRadius`。
- 四个基础锚点使用 `cellWidth/cellDepth` 的比例计算，锚点距离中心建议落在地块最小尺寸的 25% ~ 40% 内（实测取值 32.5% + 23% 抖动，最终偏移稳定在带内）。
- 偏移上限中的“地块尺寸”统一定义为 `min(cellWidth, cellDepth)`，最终槽位偏移长度落在其 25% ~ 40%。
- 槽位 Y 默认跟随 `RealCenterWorldCoordinate.y`，槽位偏移只改变 XZ；若后续需要贴合坡面，必须通过统一的地形投射接口完成，不能由各调用方自行修改 Y。

落点定义为**相对地块中心的局部偏移**：

```text
slotLocalOffset = new Vector3(lx, 0, lz)
worldPosition   = cell.RealCenterWorldCoordinate + slotLocalOffset
```

好处：

- 地块移动、高度变化、地图缩放时，落点自动跟随。
- 不同地形 / 建筑地块可以有不同的落点布局。

### 3.1.1 落点位置：地图生成时烘焙随机（已确认方案）

槽位位置**不采用全图统一的固定布局**，也**不在运行时实时随机**，而是在**地图生成阶段为每个地块随机一次并固定**，之后整局游戏只读取、不再变化。

```text
地图生成 → 为每个地块采样一套槽位偏移 → 固定
运行时   → 只读 slotId → localOffset 的映射
```

这样做保留了确定性：`slotId → 位置` 的映射在整局内稳定，因此第 3.3 节的占用状态、第五节的槽位预留、存档 / 回放 / 调试 gizmo 都不受影响。额外好处是**校验成本前移**：生成期可以做昂贵检查（落点是否落进山地模型、宝箱、建筑装饰里），命中就丢弃重采，运行时零开销。

烘焙随机必须配三条约束，否则随机会以别的形式咬回来：

**约束一：每格槽位数量固定，只随机位置。**

容量不能跟着随机（这格 3 个、那格 5 个）。否则寻路的 `CanEnterCell` 容量判断、AI 的「能不能挤进去」决策、玩家对「这格还能站人吗」的直觉预期全部变得不可推理，第六节那批规则会更难收敛。

本方案的基础容量固定为 **5**（四角 + 中心）。唯一的例外是 3.2 描述的生成期碰撞校验会把无法放置的槽位标记为 `disabled`，使个别地形格的有效容量低于 5——但该结果由「地形 + 种子」确定、整局不变、且生成期就能烘焙出来供 AI 与 UI 查询，所以仍然可推理，只是不再全图统一。

**约束二：用「抖动格点」而不是自由随机。**

基础布局是 3.1 定下的 5 个锚点（四角 + 中心），每个锚点在半径 `r` 内抖动：

```text
slotLocalOffset = baseAnchor[i] + randomInsideCircle(r)
d = 锚点间的最小两两距离（本布局中是 中心↔角 的距离）
r = d * 0.25
```

两处细节：

- **中心锚点不抖动**，固定为 `Vector3.zero`。它是 4.2 起点过渡的参照点，抖了就没有真中心可用了。
- **锚点半径 + r ≤ 偏移上限**（地块尺寸的 40%，见九.4）。四角锚点放在 25% ~ 40% 带内（实测 32.5%，抖动 23% 后仍在带内），不需要额外 clamp。

好处：

- **天然不穿模**：两锚点相距 `d`，各抖 `d/4`，最坏情况仍相距 `d/2`，无需泊松盘或拒绝采样。中心不抖时下界更宽（`d - r`）。
- **保留跨地块一致性**：同一个 slot 索引在任意地块的偏移方向大致一致，4.2 节担心的蛇形被压到「抖动量级」而非「布局量级」。

纯自由随机会丢掉第二条，这是它和抖动格点的关键差别。

**约束三：随机数从「地图种子 + 地块坐标」哈希派生，不落盘。**

```text
rng = Hash(mapSeed, cell.q, cell.r, slotIndex)
```

当前 `SeedService` 尚无该接口，需新增稳定的坐标派生方法，例如：

```text
SeedService.DeriveCellSeed(moduleId, mapSeed, q, r, slotIndex)
```

实现约束：

- 只使用整数六边形坐标和整数槽位索引，不使用世界坐标。
- 不使用依赖运行时实现的 `System.HashCode`，必须采用明确的 32 位混合算法。
- 增加独立模块常量，例如 `UnitSlot`，避免复用 Terrain、LandForm 或 AI 随机流。
- 记录 `SeedService.GeneratorVersion`；若算法或锚点公式变化导致旧地图槽位变化，存档和回放必须按版本处理。

存档只存地图种子和生成版本时，读档重算才可得到同一套落点。

### 3.2 预制落点

- 可在 `HexCellData` 上新增 `UnitSlotProvider`，负责生成 / 维护槽位。
- 槽位由代码在地图生成时按 3.1.1 的规则采样生成（基础锚点按六边形尺寸计算）。
- **槽位数据只有一个来源：种子派生的烘焙随机。不设手工 override 表。** 特殊地块（山地、祭坛、宝箱、公共建筑）同样走随机采样，靠生成期的碰撞校验保证质量。

生成期校验流程：

```text
for each slot:
    采样 slotLocalOffset
    检测该点是否落进生成期障碍代理
    命中 → 重采样，最多 N 次（建议 N = 8）
    N 次仍失败 → 该 slot 标记 disabled，本格有效容量 -1
```

当前地图生成时山地、地貌、资源数据已经存在，但地貌/资源运行时模型由 `MapPresentationBootstrap` 分帧实例化，公共建筑、主城和中央宝箱还在后续流程中生成。因此“障碍碰撞体”必须改为“生成期障碍代理”：

- 山脉使用山脉数据、有效山体范围或统一的数学包围体；
- 地貌、资源使用配置中的占用半径/高度或其他生成期代理；
- 公共建筑使用其根格、子格占位数据；
- 主城、宝箱和装饰使用生成阶段可访问的占位数据；
- 如某类障碍没有生成期代理，不得假装已经完成碰撞校验，应明确降级为“不禁用该槽位”或“整格禁用”，并记录诊断日志。

`disabled` 结果与偏移一样由“地形/障碍数据 + 种子”确定，生成期一次性写入地块数据，运行时和 AI 只读。处理某类地形站位难看时，应优先调整该地形的障碍代理或锚点半径，而不是引入第二套手工 override 数据源。

### 3.3 槽位占用状态

每个槽位需要记录：

```text
slotId
localOffset            (生成期烘焙，运行时只读)
disabled               (生成期碰撞校验失败，永久不可用)
occupiedBy (单位引用 / null)
reservedBy (移动任务 / null)
```

地块需要记录：

```text
基础容量        = 5（四角 + 中心，全图统一）
有效容量        = 5 - disabled 槽位数（生成期烘焙，整局不变）
已占用槽位数量
剩余可用槽位数量 = 有效容量 - 已占用 - 已预留
```

`CanEnterCell` 与 AI 决策一律以**有效容量**为准，不用基础容量。需要区分以下查询：

```text
HasFreeStandingSlot(cell)
HasFreeReservedSlot(cell)
IsSlotReserved(cell, slotId)
IsCellFullyOccupied(cell)
IsCellFullyReserved(cell)
```

部署、兵营生产、AI 卡牌和探索奖励必须使用“取得具体站位槽”的原子接口，不能继续只判断 `IsHaveUnit()`。

## 四、落点选择：根据「前 — 现 — 后」三点确定

对于路径中经过的当前地块 `B`，已知：

```text
前一个地块 A（从哪来）
当前地块 B（站哪里）
后一个地块 C（往哪去）
```

落点选择依据：

1. **进入方向**（A → B）；
2. **离开方向**（B → C）；
3. **转弯角度**（进入与离开的夹角）；
4. 当前地块已有单位数量；
5. 当前单位在队列中的序号；
6. 是否「尽量直」。

### 4.1 候选落点评分

可从以下评分标准中选一或组合：

- **最小转向**：让「进入方向 ≈ 离开方向」，落点使经过该格时的转角最小。
- **贴近前后连线**：取「前格中心 — 后格中心」连线，选当前地块中距该连线最近的落点。
- **分散优先**：结合队列编号，把不同单位分配到不同落点，避免都抢同一个最优点。

**建议做法（配合 3.1.1 的烘焙随机）：按几何选点，不按索引选点。**

```text
1. 取「前格中心 — 后格中心」连线
2. 在当前地块的空槽位中，选距该连线最近的一个
3. 队列中后续单位依次向外排（按到连线的距离递增）
```

即第二条「贴近前后连线」为主，队列编号只用于**排序**、不用于**指定 slotId**。

原因（与抖动量级无关，即使各格布局完全一致也成立）：

- **天然贴合行进方向**：几何选点每一步选的都是当前格里最靠近「来向 → 去向」连线的空位，所以转角天然最小；按索引固定分配时，单位 2 无论从哪个方向进来都走 slot1，遇到转弯就会出现绕行或反向偏移。
- **对已占用槽位鲁棒**：格内已有其他单位（友方驻守、战斗中、正在通过）时，几何选点只是退到次近的空位，路径形状基本不变；按索引分配会直接撞上「我的 slot 被占了」，需要另写一套回退规则，而回退后的落点与行进方向无关。
- **对有效容量变化鲁棒**：3.2 的生成期碰撞校验会让个别地块的某些 slot 为 `disabled`，各格可用索引集合不同。几何选点对此无感知；按索引分配则必须处理「slot1 在这格不存在」。

抖动带来的跨格布局差异只是让上述问题更明显一点，不是主要理由——按 3.1.1 约束二，抖动量级是 `d/4`，本身不足以否决索引分配。

### 4.2 落点序列平滑

- 相邻两格的落点偏移变化不要过大，避免蛇形摆动。
- 起点：从单位当前实际位置平滑过渡；若单位此前站在 `中心` 槽位，则偏移就是 0（中心锚点按 3.1.1 约束二固定不抖动）。
- 终点：落点偏移控制在**地块尺寸的 25% ~ 40%**（与九.4 的偏移上限同一套数值），仍远小于相邻格心距离，逻辑格反查不受影响。
- 选点完成后必须验证槽位仍属于当前任务、未被其他单位抢占；验证失败时只能从同一候选排序中重新取下一个槽位，不得在 `Update` 中临时随机。
- 视觉路径的起点不能默认取地块中心。应取单位当前实际位置；若单位当前位于攻击表现、死亡表现或地图高度动画中，必须由状态机明确禁止普通移动请求。

## 五、移动过程中的槽位预留

仅「最终落点分开」不够，移动经过中间地块时单位仍会重叠。因此需要：

- 每个路径节点（中间地块）也分配视觉落点。
- 移动任务创建时，一次性预分配整条路径的落点。

例如：

```text
单位1：A.slot0 → B.slot0 → C.slot0 → D.slot0
单位2：A.slot1 → B.slot1 → C.slot1 → D.slot1
```

### 预留模型演进

现状：

```text
_reservedDestinations： 目的地格 → 1 个单位
```

目标：

```text
(B 地块, Slot i) → 单位 X
```

即预留粒度从「地块」细化为「地块 + 槽位」。同时补充移动任务模型：

```text
MovingUnit
    logicalPath              地块坐标序列
    visualSlotPath            每个路径节点对应的 slotId
    currentPathIndex          当前视觉节点
    startCell/startSlot       取消时恢复的位置
    reservedCells             已预留的全部 (cell, slotId)
```

必须先在实现前决定以下二选一：

- **完整任务模式**：一次提交完整逻辑路径和视觉槽位路径，整条路径原子预留；
- **逐格任务模式**：保留 `UnitBrainBase` 的逐格 `MoveTo`，每次只预留下一格，到达后再选下一槽位。

当前代码采用“Brain 缓存完整路径、MovementSystem 逐格执行”的混合方式。阶段 1 不得直接套用整条路径预留，必须先定义缓存路径失效、其他单位抢占和中途容量变化的处理协议。

无论采用哪种模式，都必须保证：

- 起点站位是否继续占用由任务状态明确记录；
- 中间格只要有视觉经过任务，就必须有 `ReservedSlot`，不能只记录最终目的地；
- 任务取消、单位死亡、地形变化和目标失效时，释放整条任务持有的全部预留；
- 预留成功和释放必须是原子操作，不能出现“字典已写入但槽位未写入”的半状态；
- 满员时的行为固定为等待、排队、重寻路或失败中的一种，并且 UI、AI、部署入口共用同一判定。

### 移动途中的穿透问题（推迟到阶段 3 定型）

槽位预留只保证「同一时刻站在同一地块的单位不重叠」，**不解决路径交叉造成的移动途中穿模**。三种典型场景：

1. **交换位置（swap）**：单位1 A→B、单位2 B→A，同一帧沿近似共线的两条路径相向移动，必然在中点重合。槽位号不同也无效，因为两条路径本身几乎重合。
2. **交叉路口**：单位1 A→C、单位2 B→D，两条直线在中间某点相交，若到达该点的时间接近就会撞上。
3. **同槽位号汇合**：两个单位都选到同一 slot，从不同方向汇入同一地块，末段路径收敛到同一点，越接近终点越容易重叠。

备选方案（按代价递增）：

| 方案 | 做法 | 代价 | 能治哪些场景 |
|------|------|------|--------------|
| 错峰出发 | 同一批移动的单位加 0.1~0.2s 递增延迟 | 几十行，纯表现层 | 场景 2、3 的大部分（六边形网格上交叉点很少刚好同时到达） |
| slot 垂直偏移 | 路径插值时加一个垂直于移动方向的小偏移，按 slot 索引取正负，让相向路径变成两条略微分开的弧 | 几十行，纯表现层 | 场景 1（根治） |
| 成对分离 | 每帧只在「距离 < 2×半径」的单位对之间做一次对称横向推开（各推一半），推开量 clamp 到九.4 的偏移上限内 | 十几行，遍历顺序固定即可复现 | 残留的近距离重叠 |
| RVO / ORCA | 引入 RVO2-Unity 或 A* Pathfinding Project 的 `RVOSimulator`，把 RVO 当纯表现层的速度滤波器插在 `MoveTowards` 与 `transform.position` 之间 | 高，见下 | 通用连续空间避障 |

**RVO 暂不采用**，四点冲突：

- **与槽位预留职责重叠**：ORCA 会把单位推离它被分配的 slot，到达时可能站不到预留点上。必须在接近终点时淡出 RVO 权重、强制吸附回 slot，否则槽位系统形同虚设，而这个淡出本身不好调。
- **破坏确定性**：ORCA 求解依赖 agent 遍历顺序和浮点线性规划，跨平台 / 跨帧率不保证逐帧一致，与 3.1.1、九.3 建立的可复现性目标相悖。
- **单位会走出格子边界**：ORCA 的侧向推开量不受九.4「偏移上限 = 地块尺寸 25% ~ 40%」约束，视觉上单位可能明显跑到相邻地块上，而逻辑坐标还在原格——正是九.1 最担心的脱节被放大。加 clamp 会让 ORCA 解失效、容易抖。
- **与攻击位移状态机打架**：`UnitAttack()` 的 `GoToAttackPosition` / `ReturnToOriginalPosition` 走另一套 `MoveToTargetVector` 直接改 `transform.position`，RVO agent 位置需在这些阶段手工同步回去，否则攻击结束后单位会被 RVO 拉回上一帧位置。

另外本项目规模（六边形格子、单批移动单位数量个位数）用不上 ORCA 的任何优势（大规模人群、连续空间、动态障碍）。若后续演化到「一格站 5 个单位 + 多队同时行军穿插」且前三条方案压不住，再引入，并明确限定 RVO 只在**路径中段**生效、末段交还给槽位吸附。

**决策口径：本节方案推迟到阶段 3 选型，取决于阶段 1 跑通后的实际观感。** 现在选等于猜——真实穿模严重程度（"偶尔擦一下"还是"每次都糊在一起"）只有看到同格并列行走的画面才知道。延后不欠技术债，因为所有方案的接入点都是同一处：`UpdateMovement` 中「目标槽位世界坐标 → `transform.position`」这一步。阶段 1 需要为此预留挂载点（见九.8）。

### 同格血条重叠与合并显示（阶段 3，方案已定、待实现）

多单位同格跑通后暴露的第一个表现问题：**同一地块的多个单位血条会糊在一起**。

#### 成因

不是槽位系统没做好，是**血条的空间尺度与槽位偏移量级不匹配**：

- 血条是每个单位 Prefab 自带的 World Space Canvas 子物体，直接继承单位 `transform.position`，只加一个固定高度偏移（内层 RectTransform `anchoredPosition.y = 2.5`）。
- 运行时唯一的逐帧逻辑是 Billboard（`UIController.Update` 的 `LookAt`），**没有任何重叠处理**：不重排、不按深度排序、不淡出。全部单位 Canvas 同为 `sortingOrder = 100`。
- 因此两条血条的屏幕水平间距 = 两单位 XZ 槽位差的相机投影，而该差值被九.4 硬性限制在 `min(cellWidth, cellDepth)` 的 25% ~ 40%；血条自身却有可观的世界宽度（由 `71.97 px × 0.015 内层缩放 × 4 外层缩放` 的嵌套缩放链推算约 4.3 世界单位，**该数字为推算值，实现前必须在编辑器实测并与 `InnerRadius` 比对**）。

即：**血条宽度与槽位最大间距处于同一量级甚至更大**，所以模型分得开、血条仍重叠。加大槽位偏移不是解——九.4 的上限存在的理由是防止单位视觉上跨到相邻地块。

次要问题：所有单位 Canvas 同 `sortingOrder`，重叠部分的绘制顺序由相机深度决定，单位移动时会闪烁 / 交替穿插。

#### 选定方案：同格血条合并显示

**血条锚定「逻辑地块」而不是「视觉槽位」。** 同一地块的站立单位共用一个合并 UI，血条在其中排成列表，而不是各自浮在自己模型头顶。

这本质上是把血条这一层 UI 从「跟随视觉位置」降级回「跟随逻辑位置」，与九.1「逻辑位置与视觉位置必须分离」同源——重叠问题从根上消失，而不是靠调偏移量去躲。

**移动中的单位不参与合并，继续显示自己的血条。**

- `GetStandingUnits()` 的语义正好是「当前站在该格的单位」；移动中的单位持有 `ReservedSlot` 而非 `StandingSlot`，天然不在该集合内，判定条件是现成的。
- 移动中的单位在路径上本就是拉开的，重叠主要发生在站定后，这个切分与问题分布吻合。
- 若锚定逻辑格，移动途中会出现「模型平滑插值、血条在格心之间瞬移」的撕裂（逻辑格由 `CommitPathNode` 逐格提交），这也是必须走双模式的原因。

#### 可行性支撑（已核对代码）

1. **伤害链路不用动**：`CharacterData.healthBar` 是 `Slider` 引用，`CombatResolver` 与 `Heal()` 直接写 `healthBar.value`。合并只改这些 Slider 的挂载与排布，保留对象本身，写入方完全无感。
2. **挂载点单一**：`SpawnUIWiring.WireUnitCanvas()` 是玩家（`CardPresenter`）与 AI（`AIEntityFactory`）两条生成路径的唯一血条拼接入口，符合九.8「单一挂载点」的要求。
3. **Billboard 开销下降**：由「每单位一次 `LookAt`」变为「每多单位地块一次」，单位越多越省。
4. **身份标识可复用**：Prefab 内 `Canvas/Icon` 为 child0、`Slider` 为 child1；把 Icon 移到血条行首即可解决「哪条血条是谁」，无需新美术资源。

#### 已知成本与处理口径

- **成员变化用轮询，不用事件。** 第六节列出的写占用入口有十几处（部署、兵营、探索奖励、弹射、死亡清理、逐格 commit……），逐个挂事件既繁琐又易漏（漏一个即产生幽灵血条）。改为在 `LateUpdate` 遍历「站立单位数 ≥ 2 的地块」重排一次；这类地块为个位数量级，每格一次 `GetStandingUnits()` 开销可忽略。用轮询换掉十几个事件挂载点是本方案最划算的取舍。
- **必须按阵营分组，不能做血量聚合。** `UnitMovementSystem.CanEnterCell` 只判有效容量、**不判阵营**，敌我单位可合法同格。因此合并 UI 中会同时出现敌我血条，需按阵营分组（上下或左右分列），否则「本格我方 3 个、敌方 2 个」这一关键战术信息会被糊掉。同理，「平均血量 / 总血量」式的聚合显示不可取——敌我混格时该数值无意义。合并结果必须是 N 条独立血条排成列表。
- **双模式切换需过渡。** 站定并入列表、起步脱离列表的瞬间要处理血条归位，否则会跳变。
- **前置实测项**：上文 4.3 世界单位的血条宽度为推算值。若实测宽度接近或超过一个地块宽度，合并列表本身也会溢出到相邻地块，需先整体缩小血条，这会反过来影响列表行高与可读性设计。

#### 实施排期

**排在错峰出发 / 成对分离等移动避让之后。** 合并方案引入「移动 / 站立」双模式状态切分，与阶段 2 刚完成的槽位预留状态机耦合；在预留协议尚未经阶段 4 回归测试验证前叠加该层，出问题难以定位归属层。先做零状态的移动避让，阶段 4 完成后再实现血条合并。

## 六、占用模型改造（关键基础）

当前多处是**单单位假设**，需要逐步调整。

现状（示例）：

```text
HexCellData.GetUnit()                 // 单单位
HexCellData.SetHaveUnit(bool, go)     // 单单位
HexCellData.GetOccupant()             // 单单位
HexCellData.SetOccupant(go)           // 单单位
UnitMovementSystem._reservedDestinations  // 目的地格 → 单单位
```

目标：

```text
一个地块 → 多个单位
一个地块 → 多个槽位
一个移动任务 → 一组（地块 + 槽位）预留
```

需要明确并落地的规则：

- 多单位地块是否允许进入？
- 目标地块有空槽位时是否允许进入？
- 中间地块有单位但还有空槽位时是否允许经过？
- 地块容量满后是等待、排队还是重新寻路？
- 移动中的单位是否算占用？
- 槽位满了之后，寻路 `CanEnterCell` 应如何判断（仍阻挡，还是按容量判断）？

当前实现中除计划原先列出的文件外，以下入口也必须纳入本次改造：

- `CardPresenter`：玩家卡牌部署、部署合法性、部署提交后的占用写入；
- `AIEntityFactory` / `AICardBrain`：AI 单位生成和 AI 卡牌部署；
- `BarracksSpawner`：兵营生产单位的出生格选择和占用写入；
- `ExplorationRewardSystem` / `AIAutoExplorer`：探索奖励单位溢出生成；
- `UnitRemovalService`：站位槽、逻辑占用、攻击槽和移动预留的统一清理；
- `MeleeStrategy` / `RangedStrategy` / `ArrowTowerShooter`：格内多单位目标枚举与筛选；
- `TacticalCardPresenter` / `BuildingController` / `ExplorationService`：格内单位统计、建筑摧毁后的占领、探索冲突；
- `MapMutationService` / `MapVisualTransitionService`：同格多单位的高度吸附、取消和弹射。

所有从 `transform.position` 反查地块的代码也必须审计。视觉槽位偏移后，逻辑地块应优先读取 `UnitMovementController.CurrentHexCoordinate` 或移动任务记录，不能依赖偏移后的世界坐标反推逻辑位置。

> 说明：目前 `CanEnterCell` 把「有单位的地块」直接判为不可通行，多单位化后此规则必须重新定义。

## 八、分阶段实施建议（待确认后执行）

> 说明：原计划的「阶段 0：只做视觉落点、不动占用模型」已取消并拆入阶段 1B 至 1D。
> 原因是纯视觉阶段无法验证本方案的核心目标——单单位占用模型下 `CanEnterCell` 仍把有单位的格判为不可通行（见第六节），两个单位不可能同时处在一格，所以看不到「同格并列」，只能看到「单列行走时贴行进方向走」；同时 4.1 的选点算法第 2 步依赖「格内空槽位」查询，在单单位模型下无表可查，只能写一版临时退化逻辑再丢掉。
> 代价是首个可验证节点变远：槽位系统与占用模型改造要一起完成才能跑起来。

### 阶段 1A：占用语义和槽位数据模型 ✅

- 明确 `StandingSlot`、`ReservedSlot`、`AttackerSlot`、逻辑格位置四者的边界；
- 新增槽位数据结构和原子取得/释放接口；
- 明确同阵营、敌我双方、攻击中的单位是否允许共享一格；
- 明确满员时等待、排队、重寻路或失败规则；
- 保留兼容适配期间，禁止新增业务继续调用 `GetUnit()` 作为完整单位查询。

### 阶段 1B：槽位生成与确定性烘焙 ✅

槽位基础设施：

- 地图生成期按 3.1.1 采样并烘焙槽位（5 锚点、中心不抖动、种子派生、碰撞重采样、`disabled` 标记）；
- `HexCellData` 上新增 `UnitSlotProvider` 或等价数据对象，运行时只读；
- 新增 `SeedService` 坐标派生接口和生成版本约束；
- 使用生成期障碍代理完成校验，不依赖分帧实例化后的模型碰撞体；
- 增加槽位范围、槽位间距、不能跨格和可复现性测试。

### 阶段 1C：统一生成、部署和查询 ✅

- 普通卡牌、AI 卡牌、AI 工厂、兵营、探索奖励全部通过统一的站位槽取得接口生成单位；
- 所有 `IsHaveUnit()` 的部署判断改为有效容量判断；
- 战斗、箭塔、探索、建筑占领、战术卡牌统计全部改为多单位枚举；
- `UnitRemovalService` 统一清理站位槽、攻击槽、移动任务和逻辑占用；
- 补充真实 `UnitMovementController` 的 PlayMode/集成测试。

### 阶段 1D：移动表现与逻辑位置分离 ✅

- 按 4.1 的几何规则选择视觉槽位；
- `UpdateMovement` 把“目标槽位世界坐标 → 本帧位置”抽成独立方法；
- `CurrentHexCoordinate`、战斗、采集、索敌和地图变化逻辑只读逻辑地块，不受视觉偏移影响；
- 近战攻击表现、远程箭矢、死亡下沉和地图高度动画不得覆盖普通移动槽位位置；
- 动态地图刷新、弹射和取消逻辑必须枚举同格全部单位并保留各自槽位偏移。

占用模型：

- 改造 `HexCellData` 的占用为集合 / 槽位（`GetUnit` / `SetHaveUnit` / `Occupant` 全量排查）；

- 将 `_reservedDestinations` 升级为槽位级预留，同时保留外部调用所需的格级查询；
- 处理路径缓存失效、中途满员、预留被抢占、地形变化和任务取消；
- 处理战斗、采集、阵营等依赖单单位假设的逻辑。

建议阶段 1B 至 1D 先用单单位验证槽位采样、站位和逻辑坐标分离，随后立即放开同格多单位；这只是内部反馈节点，不作为对外验收节点。

### 阶段 2：移动过程中的槽位预留 ✅

- 按阶段 1E 选定的任务模式预分配落点；
- `_reservedDestinations` 升级为「地块 + 槽位」，并提供格级兼容查询；
- 处理满员等待 / 排队 / 绕行规则。

### 阶段 3：表现打磨 🔄（进行中）

- 落点偏移量按地块尺寸比例配置；
- 转弯平滑、起点 / 终点过渡；
- 稳定随机（地图种子 + 单位 ID + 地块坐标 + 步序）保证可复现；
- **移动避让方案选型与实现**：按第五节「移动途中的穿透问题」的方案阶梯，从错峰出发开始逐级加，够用即停；选型依据是阶段 1 跑通后同格并列行走的实际观感，不提前定。
- **同格血条合并显示**：按第五节「同格血条重叠与合并显示」实现——站立单位的血条按逻辑地块合并成分阵营列表，移动中的单位保留自身血条；成员变化用 `LateUpdate` 轮询驱动，不挂事件。排在移动避让之后、建议阶段 4 回归测试完成后再做。

## 九、风险与注意事项

1. **逻辑位置与视觉位置必须分离**：偏移只影响 `transform.position`，不能影响 `CurrentHexCoordinate`、占用、攻击范围、采集格、阵营判定。
2. **不要每帧重新随机偏移**：偏移应在移动任务创建时一次性确定，否则目标点抖动、轨迹不稳定。
3. **随机需可复现**：槽位位置采用 3.1.1 的「地图种子 + 地块坐标」哈希派生，只在地图生成时烘焙一次；单位级微抖动用「地图种子 + 单位 ID + 地块坐标 + 步序」，在移动任务创建时算一次。两者都不落盘、都可复现。
4. **偏移上限**：槽位布局按地块尺寸的 25% ~ 40% 起调（四角锚点放在 32.5%，抖动 23% 后仍在带内），仍远小于相邻格心距离、单位视觉上不会跨到相邻地块；槽位自身的烘焙抖动半径受「锚点半径 × 0.23」约束（3.1.1 约束二）。中心锚点固定为 0 偏移、不抖动。
5. **容量固定，只有位置随机**：基础容量全图统一为 5（四角 + 中心），槽位**数量**不跟着随机，只有**位置**随机。唯一的减项是 3.2 生成期碰撞校验标记的 `disabled` 槽位，它由「地形 + 种子」确定、生成期烘焙、整局不变，因此仍然可推理。`CanEnterCell` 与 AI 决策统一读**有效容量**（5 - disabled 数），不要读基础容量，也不要在运行时算。
6. **落点选择按几何、不按索引**：按 slotId 固定分配会在转弯处绕行、撞上被占槽位时无路可退、且无法处理 `disabled` 造成的各格可用索引不一致，详见 4.1。
7. **兼容单单位假设**：战斗、采集、`TryCaptureEnemyCell`、`CommitDestination`、`RestoreStartCell` 等现有逻辑都依赖单单位，改造时需全量排查。
8. **表现层避让的挂载点要在阶段 1 预留**：阶段 1 改 `UpdateMovement` 时，把「目标槽位世界坐标 → 本帧位置」单独抽成一个方法，不要把 `MoveTowards` 直接内联写在 `UpdateMovement` 里。第五节所有避让方案（错峰、垂直偏移、成对分离、RVO）都是在这一步之后对结果位置做修正，有独立方法就是加一层调用，没有就得回头重新拆调用点。当前 `PlayAttackAnim` 主路径已经以原地动画为主，但仍要兼容旧的攻击位移状态和死亡/箭矢表现。
9. **所有多单位处理必须枚举而不是取“第一个”**：`GetUnit()`、`GetOccupant()`、`GetOccupant() ?? GetUnit()` 只能在明确的兼容场景使用；战斗、箭塔、探索、建筑占领、战术卡牌、动态地图和单位删除必须遍历完整单位集合。
10. **视觉槽位偏移不能参与逻辑格反查**：凡是从 `transform.position` 调用 `WorldToHexCoordinate` 或 `GetCellByWorldPosition` 的代码，都必须确认它是在读取逻辑位置还是表现位置；单位逻辑位置优先使用 `CurrentHexCoordinate` 或移动任务记录。
11. **移动预留必须有统一清理入口**：取消移动、单位死亡、单位销毁、路径失效、地形变化和切换场景都必须释放所有 `(cell, slotId)` 预留；不能只删除最终目的地字典项。
12. **生成期碰撞校验必须定义数据来源**：运行时模型由 `MapPresentationBootstrap` 分帧生成，不能把模型 Collider 作为地图生成期必然存在的前提；没有障碍代理时必须明确降级策略。

## 十、结论

可行，且与当前 `MoveTowards` 匀速直线移动方式兼容，但必须先完成占用语义、生成期槽位烘焙、统一生成入口和多单位查询改造。核心是：

> **逻辑层继续走地块路径；表现层为每个地块提供多个槽位；单位依据「前—现—后」三点选择落点；移动时沿预分配槽位逐点移动，实现同地块多单位并列站立与并列行走。**

真正的工程重点不在移动动画，而在**站位槽 / 攻击槽分离、多单位地块占用模型、槽位预留、容量规则和清理协议**。实施顺序应为：先定义状态模型，再烘焙确定性槽位，统一所有生成和查询入口，最后改移动任务和容量寻路。纯视觉落点无法单独验证同格并列；阶段 1B 至 1D 可以先用单单位缩短反馈链，但必须紧接着完成真实多单位集成验证。
