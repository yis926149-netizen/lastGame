# 多单位场景卡顿成因分析

> 现象：单位数量达到二十个以上时出现明显卡顿。
> 性质：分析报告。**第一~五节已实施修复（见各节 ✅ 标注）**，六~十节仍为只读分析。
> 地图规模基准：`MapGenerationConfig.asset` 中 `xNumber: 20`、`zNumber: 30`、`OuterRadius: 3` ≈ **600 格**，这是下文所有「全图操作」的公共乘数。

---

## 结论先行

卡顿不是槽位系统造成的，而是 **「每帧全员决策」×「每次决策跑 N 次全图 Dijkstra」×「拥挤时节流失效」** 三层相乘的结果。

这三层单独看都能撑住 5~10 个单位，叠在一起在 20 个单位附近越过阈值，所以表现为「突然卡」而不是「逐渐变慢」。

## ✅ 一、放大器：GameLoop 每帧驱动全部 brain，无预算 —— 已修复

> **修复**：`GameLoop.Tick()` 改为**轮转式每帧决策预算**（`BrainDecisionBudgetPerFrame`，默认 8，`<= 0` 退回旧的全员驱动）。
> 游标 `_brainCursor` 跨帧保留，保证公平、不饿死；忙碌 / 暂停的 brain 不消耗预算。
> 下面描述的是**修复前**的旧代码。

`Assets/Scripts/Core/Services/GameLoop.cs:51-70` 的 `Tick()` 在**同一帧**里对每个不忙的 brain 调用 `OnStepFinished()`：

```csharp
public void Tick()
{
    if (IsPaused) return;
    GameTime += Time.deltaTime;
    for (int i = _brains.Count - 1; i >= 0; i--)
    {
        var brain = _brains[i];
        if (brain == null) { _brains.RemoveAt(i); continue; }
        if (brain.IsPaused) continue;
        if (brain.IsBusy) continue;
        brain.OnStepFinished();
    }
    TickPublicBuildings();
    _globalTimer.Tick(Time.deltaTime);
}
```

没有时间片、没有每帧决策配额、没有轮转。N 个空闲单位 = N 条完整决策链挤在一帧。

这本身只是线性开销，但它把下面每一项的单位成本都乘上了 N。

## ✅ 三、索敌是 O(候选数) 次全图寻路 → 整体 O(N²) —— 已修复

> **修复**：三个 `FindNearest*` 查询统一改为 `UnitBrainBase` 的「候选收集 → 按六边形距离升序 → 只对最近的
> `MaxPathfindCandidates`（= 6）个候选跑寻路」（`AddTargetCandidate` / `PickNearestByPathCost`，候选缓冲按实例复用），
> `AIUnitBrain` / `PlayerUnitBrain` 的索敌与 `UnitBrainBase.FindNearestChest` 共用同一套逻辑；
> `MeleeStrategy.ChooseNextPath` 的三个查询各只执行一次并在同一次决策内复用结果。
> 一次索敌从「O(候选数) 次全图 Dijkstra」降为「≤ 6 次提前退出的 Dijkstra」，且近邻候选的搜索成本正比于真实距离而非全图。
> **行为变化**：候选上限意味着「最近的 6 个候选全部不可达」（如隔海相望）时查询返回 null，不再尝试更远候选 ——
> 这正是把最坏情况压成常数的代价；并列代价的目标取舍由距离排序决定，可能与旧实现的候选迭代序不同，但仍是确定、可复现的。
> 下面描述的是**修复前**的旧代码。

这是「20 个才卡」而不是「平滑变慢」的**核心原因**。

- `AIUnitBrain.cs:53-63` / `PlayerUnitBrain.cs:69-82` 的 `FindNearestEnemy()`：**对每一个敌方单位跑一次完整 Dijkstra**。
- `AIUnitBrain.cs:87-122` / `PlayerUnitBrain.cs:107-139` 的 `FindNearestEnemyBuilding()`：遍历全图格，**对每个建筑格跑一次完整 Dijkstra**。
- `UnitBrainBase.cs:250-258` 的 `FindNearestChest()`：**对每个宝箱跑一次完整 Dijkstra**。

唯一的剪枝是：

```csharp

```

拿六边形直线距离和累计移动代价比较 —— 在单格 cost 基本为 1 的地形上剪不掉多少。

于是：**N 个单位 × N 个敌人 = N² 次全图 Dijkstra / 帧**。

| 单位数 | 每帧全图 Dijkstra 次数（量级） |
|---|---|
| 10 | ~100 |
| 20 | ~400 |
| 30 | ~900 |

每次 600 格。这就是阈值感的来源。

## ✅ 四、最贵的分支恰好是「没目标」时走的兜底 —— 已修复

> **修复**：`ChooseFallbackPath` 整段兜底从「最多 3 次全图 Dijkstra + 1 次全图洪泛」压成**一次洪泛**。
> 在 5a 入口先跑一次 `GetAllReachableHexesFromStartHex`，结果同时供两处使用：
> ① 灌进实例复用的 `HashSet<Vector3> _reachableSet`，`FirstUnreachable` 的可达性判定退化为 **O(1) 查表**；
> ② 同一份 `List` 直接喂给新拆出的 `FindClosestCellToTargetIn` 选岸格，不再二次洪泛。
> `FindClosestReachableCellToTarget`（公开 API）保留，内部改为「洪泛 + 调用 `FindClosestCellToTargetIn`」。
> 只剩最后那次求岸格路径的 Dijkstra —— 而它有提前退出。
>
> **等价性要点**：旧 `IsReachable` 用的是 `MovementPurpose.MoveToAttack`，该模式允许**终点本身被占据/不可进入**
> （走到邻格即可开打）；而洪泛传的 `allowedBlockedTarget` 为 null，站着敌人的格子不会出现在可达域里。
> 若直接查表就会把近身敌人误判成「被隔绝」，错误地送进隔海趋近。
> 故新增 `IsReachableForAttack`：目标格本身在集合内 **或其 6 个邻格任一在集合内** 即算可达
> （`CubeNeighborOffsets` 与 `HexMapService.GetNeighbor` 的 NE/E/SE/SW/W/NW 一一对应）。
>
> **行为变化**：邻格判定是「一步可达邻格 ⇒ 可攻击」的几何近似，与旧的 MoveToAttack 寻路结论在
> 常规地形上一致；理论上若某敌人的全部邻格都不可通行、仅其自身格可作为 MoveToAttack 终点，
> 旧实现判可达而新实现判不可达 —— 但那种格子本就走不进去，判为隔绝反而更贴合语义。
> `FirstUnreachable` 仍保持惰性求值（前一级命中就不扫后一级，建筑查询要遍历全图格）。
> 下面描述的是**修复前**的旧代码。

`UnitBrainBase.cs:429` 的 `ChooseFallbackPath` 一次要跑：

1. `FirstUnreachable`（`UnitBrainBase.cs:391`）—— 最多 3 次 `IsReachable`，**每次一个全图 Dijkstra**
2. `FindClosestReachableCellToTarget`（`UnitBrainBase.cs:321`）—— `GetAllReachableHexesFromStartHex(allPoints, startHex, allPoints.Count, FactionId)`，预算等于全图格数的**完整洪泛**
3. 最后一次 `CalculateMinMovementCostBetweenTwoHexes` 求岸格路径

= **单个空闲单位、单帧、5 次以上全图搜索**。

而「隔海相望 / 挤不进去 / 没目标」正是单位多时最常见的状态。另外 `PickRandomWanderTarget`（`UnitBrainBase.cs:368`）也要跑一次 `GetAllReachableHexesFromStartHex`。

> 游走那次洪泛保留原样：第 2.6 节加入预算剪枝后，半径 3 的调用只展开几十格，已不是热点。

## ✅ 五、拥挤 → 节流失效 → 每帧重算的正反馈（20+ 的直接触发器）—— 已修复

> **修复**：`MoveTo` 的返回值不再被吞掉。
> `IUnitMovement.MoveTo` 与 `UnitMovementController.MoveTo` 由 `void` 改为 `bool`
> （false = 死亡调度中 / `MoveToAttack` 但目标已失效 / `RequestMove` 被拒，最常见的就是整路径槽位预留失败）；
> `UnitBrainBase.OnStepFinished` 的两个调用点在收到 false 时调用新增的 `OnMoveRejected()`：
> **作废缓存路径**（`InvalidatePath`，目标格已被别人占住，沿旧路径继续只会一步步撞同一堵墙）
> **并置 `_pathfindFailed = true`**，让既有的 `SearchInterval` 节流真正介入，把重试摊到若干帧。
> 至此第五节那条正反馈被掐断：预留失败的单位会安静等待若干帧，而不是每帧重跑整条决策链。
>
> **契约保留**：`MoveToAttack` 且路径为空时 `RequestMove` 会同步调用 `OnMoveFinished` 并**仍返回 true**，
> 这一支照旧返回 true —— 请求本身是成功的，只是同帧完成。
> **行为变化**：拥挤时单位的重试频率从「每帧」降为「每 `unitPathSearchThrottle`（20）帧」，
> 观感上抢不到位置的单位会原地停顿更久再尝试，而不是持续抖动。
> 下面描述的是**修复前**的旧代码。

`UnitBrainBase.cs:205-209` 的节流（配置值 `unitPathSearchThrottle = 20`）**只在 `ChooseNextPath` 返回 null 时才生效**：

```csharp
if (_pathfindFailed)
{
    _idleSearchCounter++;
    if (_idleSearchCounter < SearchInterval) return;
}
```

但单位多时的失败形态**不是**「找不到路」，而是「找到了路但抢不到槽位」：

```text
RequestMove
  → ReservePathSlots 整路径原子预留失败
  → RequestMove 返回 false
  → UnitMovementController.cs:186-192 直接 return，isMoving 仍为 false
  → brain 下一帧仍然空闲
  → OnStepFinished 从头再跑一遍第二~四节的全部开销
```

关键点：此时 `_pathfindFailed` **从未被置位**（`ChooseNextPath` 返回的是有效路径，失败发生在更下游的 `RequestMove`），**节流完全不介入**。

于是形成正反馈：

> 单位越多 → 格子越满 → 预留失败越多 → 越多单位每帧无节流地重算全图寻路 → 更卡

这解释了为什么卡顿是在某个单位数附近**突然**出现的，而不是随单位数平滑劣化。

相关代码：`UnitMovementController.cs:184-192`

```csharp

if (!success)
{

    attackedUnit = null;
    return;          // ← isMoving 保持 false，brain 下帧继续空转

```

> **✅ 已修复（优先级表第 7 项）**，两条腿一起改：
> 1. `TryWorldToHexCoordinate` 建格心空间哈希（`Initialize` 时分桶，桶边长 = 相邻格心间距 d）。因为接受阈值 `cellRadius = d/√3 < d`，阈值内的格心必定落在查询点所在桶的 3×3 邻域，查询与线性扫描等价但为 O(1)。
> 2. 所有**单位**相关的反查改读逻辑格：策略层走新增的 `UnitBrainBase.SelfHexCoordinate`，控制器/战斗/UI 走 `UnitMovementController.CurrentHexCoordinate`。同时给该缓存补了 `InvalidateHexCoordinateCache()`，在两处绕开 `OnMoveFinished` 的跨格改写（中止移动回退起点、拥挤弹出 `MigrateOccupancy`）处调用。
>
> 仍保留世界坐标反查的是射线命中点（拖拽落点、点击选格）和建筑/出生点等无槽位偏移、非每帧的路径 —— 那里语义上就该按世界坐标算。

## 九、GC 压力 —— 这是「卡顿」而非「稳定低帧」的原因

上面每一条都在每帧产生垃圾：

- 全图 `List<Vector3>` 拷贝（第 2.7 节）
- Dijkstra 的逐节点 Dictionary / List（第 2.4 节）
- 全图 Keys/Values List 拷贝（第 2.3 节遗留调试循环）
- `GetStandingUnits()` 的 List（第七节）
- LINQ 闭包（`UnitService.cs:113`）

20 个单位时每帧的分配量足以让 GC 频繁触发，表现就是**周期性掉帧尖峰**（卡顿），而不是均匀变慢。

**判据**：如果实测观察到的是一顿一顿的卡而非持续低 FPS，GC 就是最直接的表征层原因；用 Profiler 看 `GC.Alloc` 与 `GC.Collect` 尖峰即可确认。

## 十、次要成本

- **每单位一个 World Space Canvas + 每帧 `LookAt`**：`UIController.cs:177-190`。每个 Canvas 自成一个 batch，单位越多 draw call 越多。这正是《计划》阶段 3「同格血条合并」要解决的问题，目前尚未实现。
- **`Debug.Log`**：`UnitMovementController` 在 `isMoving` 状态切换和 `StartAttackSequence`（`Debug.Log($"[Attack] Recorded AttackerPosition: {attackerPosition}")`）里有日志。Unity 的 `Debug.Log` 带堆栈收集，在高频状态切换下成本可观。
- **`FactionOf(GameObject)`** 每次调用都做 `unit.GetComponent<UnitMovementController>()`。
- **`IsUnitMoving`**（`UnitMovementSystem.cs:592`）线性扫 `_movingUnits`。

后两项相对前面几项属于噪声级。

## 明确排除：槽位系统不是原因

考虑到最近的提交是 `70239eb1b 实现多单位进入同一地块（未优化性能和表现）`，很自然会怀疑槽位系统。

但 `Assets/Scripts/Core/Models/UnitSlotProvider.cs` 的每个操作都是 `SlotCount = 5` 的定长循环，`Bake` 只在地图生成期执行一次，运行时只读。它的直接开销可以忽略。

**它的真实作用是触发器**：多单位同格让第五节的「预留失败 → 无节流重算」路径变成常态，把原本就存在的 O(N²) 全图寻路成本暴露了出来。

性能问题在多单位特性之前就已埋好，只是那时一格只能站一个人、单位密度上不去而已。
