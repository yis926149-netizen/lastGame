# 改造方案讨论总结

## 一、改造目标

1. 删除科技树、文化树系统
2. 将回合制改为实时
3. 玩家不可操作某个具体单位——每种类型的单位有其自动化逻辑
4. 新增时间停止按钮

---

## 二、关键决策

**实时化粒度：方案 B——真实时**
彻底移除回合概念，所有单位和 AI 持续 Update tick，结算逻辑改为事件/条件触发。

---

## 三、现有架构分析

### 3.1 回合驱动现状

- 回合推进完全靠按钮触发，无任何时间驱动。
- `GameStateMachine.EndTurn()` 是唯一入口，由 `UIController.NextTurn()` 调用。
- 阶段流程：`PlayerPhase → AIPhase → SettlementPhase → NextTurn`。
- AIPhase 跑完协程后自动推进到 SettlementPhase，再切回 PlayerPhase，玩家无法干预中间过程。

### 3.2 AI 系统现状

- AI 已经是协程驱动的，`AIManager.ExecuteAITurn()` 逐单位串行执行决策。
- `AITacticalBrain.HandleSingleUnitTurn(CharacterData cd)` 接受任意 `CharacterData`，通过 `IUnitMovement` 接口控制，与单位是玩家还是 AI 无关。
- AI 受逻辑迷雾约束，只能追击视野内的目标；无目标时向迷雾边缘游走。

### 3.3 单位移动现状

- 已经是实时动画：`UnitMovementSystem.Tick()` 每帧驱动，`Vector3.MoveTowards` 以 20f/s 逐格移动。
- 攻击也是实时动画序列（冲刺 → 攻击动画 → 返回原位）。
- 这部分不需要改动。

### 3.4 科技/文化系统依赖

涉及约 20 个文件的改动，详见第五部分。

---

## 四、改造方案（按实施顺序）

### 第一步：实时化（最核心）

**新的 GameLoop（替代 GameStateMachine）：**

```
GameLoop
├── bool isPaused（对应第四步的暂停按钮）
├── float gameTime（累计游戏时间）
├── Tick() 每帧：
│   ├── 若 isPaused → 跳过
│   ├── 驱动玩家单位自动行为
│   ├── 驱动 AI 行为
│   └── 驱动结算逻辑（定时器触发，如每 N 秒）
```

**需要删除/重构的：**
- `PlayerPhase`、`AIPhase`、`SettlementPhase` 三个类删除
- `IGameStateMachine` 接口简化为暴露 `isPaused`、`GameTime`、`OnTick` 事件
- `UIController.NextTurn()` 按钮改为"暂停/继续"按钮

**结算逻辑迁移：**
- 回血：单位站在农田/祭坛上时，每隔 X 秒触发（定时器）
- 死亡清理：单位死亡时立即触发（事件驱动），不需要结算阶段

**AI 改造：**
- `AIManager.ExecuteAITurn()` 从每回合跑一次改为持续运行的协程
- 每个单位有自己的"冷却时间"（例如每 3 秒决策一次）

## 五、已确认的设计决策

### 5.1 单位自动化行为策略 —— 已定（逐格决策 + 单位基类）

#### 决策节奏：逐格决策

单位遵守棋盘规则按格子移动，**每到达一格就触发一次决策，决定下一格走哪**。

- 决策的时间间隔天然由"走一格的动画时长"决定，不需要额外的决策计时器；
  移动速度慢的单位决策频率自然就低。
- `UnitMovementSystem.Tick()` 到达终点后的 `OnMoveFinished()` 回调，就是天然的决策触发点。
- 采用"真逐格"实现：每次只 `MoveTo(相邻格)`，走一格停一下再决策，响应最灵敏
  （中途出现新目标可立刻转向）；单位数量不多，重复寻路开销可忽略。

决策循环：

```
到达一格 → OnMoveFinished() → UnitBrain.OnStepFinished()
    ├── if CanAttack() → DoCombat()        // 先判断作战
    └── else → 走 ChooseNextStep() 选出的下一格   // 否则移动
                  → 到达后再次触发 OnStepFinished()
```

#### 结构：单位基类（分玩家/AI）+ 策略组合（分兵种）+ 装饰器链（buff）

差异有三个维度，分别用不同机制处理，避免子类数量爆炸：

| 差异维度 | 机制 | 类数量 |
|---|---|---|
| 玩家 vs AI（目标/迷雾来源不同） | **继承** `UnitBrainBase` | 2 个 |
| 兵种（移动/作战策略不同，十几种以下） | **组合** `IUnitStrategy` | N 个策略 |
| buff（改数值 / 改行为） | **装饰器链**包裹策略 | 每 buff 1 个装饰器 |

> 关键前提：buff 不只是改数值，**还能改变移动/作战逻辑本身**（例如狂暴见谁打谁、
> 恐惧转为逃跑），因此兵种策略必须可运行时热替换 —— 这是选用策略 + 装饰器而非
> `switch(UnitID)` 的根本原因。

**第一层：`UnitBrainBase`（MonoBehaviour），只分玩家/AI**

```
UnitBrainBase : MonoBehaviour
│
├── CharacterData Owner                     // 关联数据
├── IUnitStrategy activeStrategy            // 当前生效策略（运行时是一条装饰器链的头部）
│
└── void OnStepFinished()                    // 【共有骨架，不可覆写】固定优先级流程
        ├── if activeStrategy.CanAttack() → activeStrategy.DoCombat()
        └── else → MoveTo(activeStrategy.ChooseNextStep())

PlayerUnitBrain : UnitBrainBase   // 提供 IsVisible（玩家迷雾）的目标查询
AIUnitBrain     : UnitBrainBase   // 提供 AIFogService 的目标查询（迁移复用 AITacticalBrain 逻辑）
```

共有部分（基类固定）：逐格决策循环机制、"先作战否则移动"的优先级、走一格用
`UnitMovementSystem`（棋盘规则、格子代价）。

**第二层：`IUnitStrategy`（兵种策略，组合注入）**

```
IUnitStrategy
├── Vector3? ChooseNextStep()   // 选下一格
├── bool CanAttack()            // 能否攻击
└── void DoCombat()             // 执行攻击

实现（按 UnitID 装配一个基础策略）：
├── SettlerStrategy   // 找空地/建城，CanAttack 恒 false
├── MeleeStrategy     // 朝目标走，贴脸才打
└── RangedStrategy    // 朝目标走，射程内就打
   ...（十几种以下）
```

**第三层：buff 装饰器链（运行时热插拔）**

```
StrategyDecorator : IUnitStrategy     // 抽象装饰器，持有 inner（被包裹的策略）
├── 完全替换型 buff：方法内不调用 inner，直接返回自身逻辑（原逻辑被短路）
│      例：BerserkDecorator（狂暴，无视原目标选择，见谁打谁）
└── 叠加修改型 buff：方法内先/后调用 inner，在结果上加工（原逻辑保留并被修改）
       例：SlowDecorator（减速，改一格步长/耗时，其余转发 inner）
```

运行机制：
- **单位创建**：`activeStrategy = new MeleeStrategy(...)`（裸兵种策略）
- **buff 生效**：往外包一层 → `activeStrategy = new BerserkDecorator(activeStrategy)`
- **多 buff 叠加**：继续往外包，形成链 → `Fear( Berserk( Melee ) )`；
  调用从最外层进入，每层决定自己处理还是转发 `inner`
- **buff 失效（重建法）**：单位维护当前生效 buff 列表，任一 buff 变动时，
  从裸兵种策略开始按顺序重新套一遍链（单位 buff 数量少，重建开销可忽略；
  比"链表摘中间节点"简单可靠）

移民单位（UnitID==0）：装配 `SettlerStrategy`，`CanAttack()` 恒 false。

#### 与现有架构的衔接

- `IUnitMovement.OnMoveFinished()`（目前空回调）改为调用 `unitBrain.OnStepFinished()`
- `AITacticalBrain` 逻辑拆解后迁移进 `AIUnitBrain`，`AIManager.ExecuteAITurn()` 整体废弃
- `PlayerInputHandler` 的单位移动/攻击输入逻辑删除，卡牌拖拽和镜头控制保留

- **结算间隔**：下放到各建筑/地貌数据类

### 5.4 移动力字段处置 —— 已定

实时化 + 逐格决策后，"每回合移动配额"概念消失，移动力字段分两种语义处理：

| 字段/方法 | 处置 | 说明 |
|---|---|---|
| `IUnitMovement.RemainingMovement`（每回合配额） | **删除** | 无回合概念，配额机制失效 |
| `UnitData.MovementPoints` | **保留，语义改为"移动速度"** | 供 `UnitMovementSystem` 动画速度参数用，区分快慢单位 |
| `UnitMovementSystem.RequestMove()` 内移动力校验 | **删除** | 不再限制单次可走格数 |
| `GameStateMachine.ResetForNewTurn()` 里 `RestoreUnitMovementStandbyParameters()` | **删除** | 不再每回合重置移动力 |
| `AIManager.ExecuteAITurn()` 里同名重置调用 | **删除** | 同上 |
| `IUnitMovement.GetReachableHexes()` | **删除或仅留 UI 高亮用** | 逐格决策每次只走一格，无需预算可达范围 |

### 5.5 攻击/战斗系统重构 —— 已定

#### 现有攻击逻辑的问题（为何重构）

- 表现与逻辑死耦合：扣血发生在攻击动画特定帧（`CommenceAttack`），靠
  `isAttacked`/`attackNumber` 一堆 bool 标志跨对象通信
- 锁死约 3 秒：`Invoke(..., 1.5f)` 硬编码延时 + `IsBusy` 锁整个单位
- 回合制残留：攻击后 `currentMovementPoints = 0`，实时化后无意义
- 与新的策略/装饰器架构不搭：攻击逻辑需能被 buff 装饰器改写

#### 核心原则：逻辑与表现分离 + 无"回合/防守方"概念

```
IUnitStrategy.DoCombat()                          // 策略层：决定打谁、怎么打
    ├── CombatResolver.Resolve(attacker, target)  // 逻辑层：纯数据结算（瞬间扣血/死亡）
    └── UnitMovementController.PlayAttackAnim(...) // 表现层：只播动画，不含逻辑判定
```

- **瞬间结算**：`DoCombat` 调用即完成扣血，动画只是回放，动画时长不影响结算结果
- **无反击**：实时相互攻击，近战/远程单位都是"进入攻击范围就一直打，直到目标死亡"
- **无防守方概念**：不区分攻/防，双方都是"攻击范围内有敌人便开打"
- **攻击后摇 = 攻速**：新增攻速字段到 `UnitData`（如 `AttackInterval`），可被 buff 装饰器修改

#### 攻击范围定义（外扩 n 环）

攻击范围为 n，即以单位当前所在地块为中心向外扩 n 环：

| 单位 | range | 可攻击范围 |
|---|---|---|
| 近战 | **0** | 仅同格（必须走进敌人所在格才能攻击）|
| 远程 | ≥1 | 同格 + 外扩 n 环内所有格 |

> 注意：`UnitData.BasicAttackRange` 的语义随之调整，近战从原来的 1 改为 0。

#### 同格交战模型（方案 B：真同格）

近战攻击时**真正走进敌人所在格**，与敌人同格共存。为防止无限围殴，引入
**六方向进攻槽位**：

```
        [槽0]
   [槽5]      [槽1]
        目标格           一格最多被 6 个近战单位围攻
   [槽4]      [槽2]      每个方向槽只能有一个进攻单位
        [槽3]
```

- **槽位方向 = 进攻方来的方向**：单位从 A 格走向敌人格 B，占据"B 格朝向 A 的方向槽"
- **方向槽满 = 移动力 ∞**：寻路计算下一格代价时，若某相邻格是敌人格且"我要进入
  的那个方向槽已被占"，则该格代价 = ∞，寻路自然绕开；普通空格不受影响。
  用移动代价统一表达槽位占用，无需单独写选槽逻辑
- **远程不占方向槽**：远程隔空攻击，不进入目标格，范围内即可攻击，无 6 方向数量限制

#### 决策与状态流程（逐格 + 攻击态）

无固定"防守方"，每次决策即时判定移动或攻击：

```
每次决策触发（到达一格 / 攻速周期结束 / 目标死亡事件）：
│
├── 扫描攻击范围（近战=能走进的敌人格 / 远程=range 环内所有格）有无敌人
│
├── 有敌人 且（近战：能占到方向槽 / 远程：在射程）：
│      → 进入/维持攻击态，原地按攻速 CombatResolver.Resolve() 瞬间结算
│      → 目标死亡 → 立即以【当前所在格】为起点重新决策
│            （直接离开，不回当前格中心再走）
│
└── 无敌人 或 想打的敌人格方向槽全满(∞)：
       → 移动态，寻路选下一格（∞ 代价格被绕开）→ MoveTo(下一格)
```

决策触发时机补充（Engaged 态不走格子，需额外触发点）：
- 每到达一格 → `OnStepFinished()`（移动中）
- 每个攻速周期结束 → 检查目标是否还活着/在范围内（交战中）
- 目标死亡事件 → 立即重新决策（交战中被动触发）

#### 碰撞逻辑（纯代码，非 Unity 组件）

- **目的**：仅解决近战同格交战时**模型视觉重叠**，属表现层
- **实现**：纯代码计算，不使用 Unity Collider 组件。同格的多个进攻者按其占据的
  方向槽，把模型摆到目标格对应方向的边缘错开显示
- 移动时能否重叠属另一问题（见 6.3），此处不涉及

#### 需要新增/改动的关键点

- `HexCellData` 占用模型重构：区分"格子主人（Occupant，单值）"与"6 方向进攻槽
  （AttackerSlots）"；`SetHaveUnit/IsHaveUnit/GetUnit` 拆成两套访问器
- `UnitMovementSystem`：预占、`CanEnterCell`、`CommitDestination` 区分"移动进入"
  （占主人位，要求空格）与"进攻进入"（占方向槽，方向满则 ∞）
- 新增 `CombatResolver`：纯逻辑伤害结算（复用现有 `AttackDataComputation` 公式）
- `UnitMovementController`：攻击逻辑剥离，仅保留 `PlayAttackAnim` 表现

### 5.6 多单位移动冲突处理 —— 已定

问题本质：现有预占机制（`_reservedDestinations`）隐含"串行执行"前提，回合制下
永不冲突；实时并发下多个单位可能同时/先后争抢同一目的地格。因采用逐格决策，
冲突粒度极小（只是"下一格"之争，非整条路径）。

核心原则：**一格一主 —— 任意时刻一个格子的主人位最多被一个单位拥有或预定。**
移动的主人位不允许重叠；只有攻击态才允许同格（方案 B，占方向槽）。移动与攻击
用两套占用语义，互不干扰。

三类冲突的处理：

| 冲突 | 处理 |
|---|---|
| **空格争抢** | 决策顺序化 + 先到先得 + 落败方当帧重规划 |
| **移动途中格** | 保留现有预占机制（预占 X 后他人不可选 X），实时下依然正确 |
| **交换位置死锁（对穿）** | A、B 互为目标且相邻时，原子交换两者格子归属，视觉上擦身而过 |

关键实现要点：

1. **决策顺序化**：所有单位决策在同一个 `GameLoop.Tick` 内**顺序**执行（不并行）。
   Unity 逻辑本身单线程 tick，只要决策不并行，"同时冲突"自动消解为"先后"——
   遍历到 A 时 A 先占，遍历到 B 时 X 已被占，B 自然退让。现有预占机制直接复用。
2. **落败即重规划**：抢不到就在当帧换次优相邻格；次优也被占则继续退让，
   最差原地不动等下次决策。逐格决策下重选代价极小。
3. **优先级规则**：谁先预占谁优先（遍历顺序天然决定，零额外逻辑）。遍历靠前的
   单位有微弱优势，可接受。
4. **唯一需新写的**：对穿死锁的检测与原子交换逻辑。

## 六、待确认的设计问题

### 6.1 回血计时器归属（祭坛/农田）—— 已定（方案 B：挂在单位）

选**方案 B**：计时器挂在单位身上，间隔参数从脚下的建筑/地貌数据读取。

理由：
- 单位本就在持续 tick（逐格决策 + 攻速周期），顺便检查脚下地块是自然延伸
- 农田（无实例地貌）和祭坛（建筑实例）可以**统一处理路径**，无需方案 A 里对农田的特殊兜底
- 避免建筑反向查询"谁站在我上面"
- 暂停/死亡处理更干净：单位 tick 停则计时停，单位销毁则计时器随之消失

每个单位持有两个计时器（或一个通用计时器 + 当前来源引用）：

```
UnitBrainBase / CharacterData
├── float _landHealTimer      // 地貌回血计时（农田）
└── float _buildingHealTimer  // 建筑回血计时（祭坛）

每 tick：
├── if 脚下 landFormType == FromLand → 累加 _landHealTimer
│       到 LandFormConfigSO.HealInterval → Heal(HealRatio * maxHp)，重置计时
└── if 脚下有 Altar 建筑 → 累加 _buildingHealTimer
        到 BuildingData.HealInterval → Heal(AltarValue * maxHp)，重置计时
```

间隔参数仍在数据类（`LandFormConfigSO.HealInterval`、`BuildingData.HealInterval`），
符合 5.3 已定的"结算间隔下放到各建筑/地貌数据类"原则。

### 6.2 buff 叠加规则 —— 已定

**数值类 buff**（攻击力、防御、移速、攻速、射程等）走**加算**，相反 buff 相互抵消。
加算天然无序，顺序问题消失。

公式封装在唯一入口 `BuffAggregator.Compute(baseValue, activeBuffs, statType)`，
不在 `CharacterData` 里直接做算术。后续若改为乘算或混合算法，只改此方法，
其余代码不动。

**行为类 buff**（改决策逻辑，如狂暴、恐惧）：现阶段不存在行为类 buff，
装饰器架构预留但**置空不实现**。后续新增行为类 buff 时再定互斥/叠加规则。
