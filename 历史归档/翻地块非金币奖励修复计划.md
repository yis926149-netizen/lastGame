# 翻地块奖励链路断点定位与修复计划（按现有设计）

> 本文件只按当前 Excel、Schema、运行日志和现有代码设计分析，**不改变既定玩法**。
>
> 已明确保留的设计：
> - 奖励类型权重五类各 20%；
> - `unitCountTiers` 允许 `0`，表示军事奖励中的空奖励；
> - `building.gold_mine` 允许作为建筑奖励；
> - 建筑奖励不能放置时按预生成金币降级；
> - 战术卡奖励可以使已有卡牌数量增加；
> - 奖励由地图生成阶段预生成，探索阶段只消费快照，不重新随机。

## 1. 当前配置是否已经写好

### 1.1 Excel → CSV → Unity 资产已确认同步

原始 Excel：`Config/Excel/游戏数值配置.xlsx`

生成 CSV：

- `Config/Generated/Csv/探索奖励配置.csv`
- `Config/Generated/Csv/探索奖励池.csv`

Unity 运行库：

- `Assets/GameConfig/Generated/ExplorationRewardConfigDatabase.asset`
- `Assets/GameConfig/Generated/ExplorationRewardPoolDatabase.asset`

已核对结果：

- 探索奖励配置 CSV 的 SHA-256 与 `Config/Generated/game-config.manifest.json` 一致；
- 探索奖励池 CSV 的 SHA-256 与 manifest 一致；
- 生成资产中的权重、档位和奖励池与 CSV 一致；
- `GameScene.unity` 已绑定 `_explorationRewardConfigDbSO` 和 `_explorationRewardPoolDbSO`；
- Excel 中确实配置了弓兵、剑客、两张战术卡和金矿。

因此本问题不是“Excel 没写”或“Excel 没导入”。

### 1.2 当前 Excel 内容的真实语义

探索类型权重：

```text
None=20, Gold=20, MilitaryUnit=20, TacticalCard=20, Building=20
```

军事单位数量：

```text
0,0,0,1,1,2
```

按现有 Schema，0 是合法的“空奖励”，不能擅自改成全正数。它会造成军事类型抽中后有 50% 概率生成 0 个单位，但这属于设计语义，不是数据断点。

建筑奖励池：

```text
Building -> building.gold_mine
```

Schema 已明确“金矿允许作为建筑奖励”，不能因为旧脚本注释中的“请勿放入 GoldMine”就直接移除金矿。应先定位金矿奖励实际失败在哪一步。

## 2. 已确认的奖励主链路

### 2.1 预生成链路

调用顺序：

```text
GameFlowManager.Initialize()
  -> PublicBuildingGenerator.GenerateAll()
  -> MapGenerator.GenerateExplorationRewards()
  -> ExplorationRewardProvider.GenerateReward(random)
  -> cell.SetExplorationReward(reward)
```

关键代码：

- `Assets/Scripts/Managers/GameFlowManager.cs` 74-79 行；
- `Assets/Scripts/Managers/MapGenerator.cs` 348-361 行；
- `Assets/Scripts/Core/Services/Exploration/ExplorationRewardProvider.cs` 47-155 行。

当前 Provider 按 Excel DB 和奖励池工作：

- 类型由 `ExplorationRewardConfigDatabaseSO.Config` 权重决定；
- 单位通过 `UnitBalanceDatabaseSO.unitId → legacyId → IUnitDataProvider.TryGetUnitConfig()` 解析；
- 战术卡通过 `TacticalCardDatabaseSO.cards[].cardId` 解析；
- 建筑通过 `BuildingBalanceDatabaseSO.buildingId → legacyId → IBuildingDataProvider.TryGetBuildingConfig()` 解析。

### 2.2 探索消费与结算链路

```text
ExplorationService.TryExplore()
  -> _collectionService.HarvestForGold()
  -> targetCell.TakeExplorationReward()
  -> Broadcast(Explored)
  -> ExplorationRewardSystem / AIAutoExplorer 结算
  -> Broadcast(Settled)
  -> 动画奖励点 Broadcast(RewardPoint)
```

关键代码：

- `Assets/Scripts/Core/Services/Exploration/ExplorationService.cs` 100-151 行；
- `Assets/Scripts/Core/Services/Exploration/ExplorationRewardSystem.cs` 48-123 行；
- `Assets/Scripts/AI/AIAutoExplorer.cs` 140-187 行。

`HarvestForGold()` 的基础金币与随机探索奖励是两条独立路径。日志中的“探索 +5 Gold”不能证明随机奖励类型是金币。

## 3. 真正断点：目前已确认与待确认项分开处理

### 3.1 断点 A：军事奖励 x0 是设计允许的空奖励，不是链路断点

代码路径：

```text
RollUnitCount()
  -> 0
  -> GenerateReward() 创建 UnitConfigs[0]
  -> ExplorationRewardSystem.Settle()
  -> unitCount=0，不调用 SpawnUnitsWithOverflow()
  -> 发布 Settled(MilitaryUnit)
```

日志：

```text
[ExplorationReward] 地块 ... 军事单位奖励 x0
```

结论：

- 这部分不是 Excel 丢配置；
- 不是单位映射失败；
- 是“合法空奖励”没有被 UI/日志明确说明，玩家容易误以为没有奖励。

按现有设计，后续只能修复表达和统计：显示“军事奖励：空”，而不是显示为一次成功获得了军事单位；不能把 0 档强行改掉。

### 3.2 断点 B：非金币基础金币来自另一条收割链路

`ExplorationService.TryExplore()` 127 行始终调用：

```csharp
int harvestReward = _collectionService.HarvestForGold(targetCell, factionId);
```

随后才消费探索随机奖励快照。资源收割会把地图资源转成金币，所以即使随机奖励是 `None`、军事 x0 或战术卡，玩家仍可能看到金币变化。

这解释了“翻地块只有金币”的一部分错觉，但不能解释所有非金币失败。

### 3.3 断点 C：战术卡首次探索存在初始化时序风险

配置和资源本身均存在：

- `Assets/Scripts/ScriptableObjects/TacticalCard/TacticalCard--BattleOrder.asset`；
- `Assets/Scripts/ScriptableObjects/TacticalCard/TacticalCard-Repair.asset`；
- `Assets/Scripts/ScriptableObjects/TacticalCard/TacticalCardDatabase.asset`；
- `Assets/GameConfig/Generated/TacticalCardBalanceDatabase.asset`。

但初始化顺序为：

- `GameFlowManager` 明确设为 -30；
- `CardPresenter` 明确设为 -20；
- `TacticalCardPresenter` 仅注册为 `IInitializable`，未设置执行顺序；
- `GameFlowManager.Initialize()` 会在地图初始化后直接开始游戏准备，而探索奖励系统也是 `NonLazy` 创建并监听广播。

`TacticalCardPresenter.Initialize()` 在 44-97 行才设置 `_cardPrefab`、`_cardViews` 和初始卡牌。`AddCardWithFly()` 在 156 行开始依赖这些运行时状态。

运行日志反复出现：

```text
[ExplorationReward] 战术奖励但无法发牌（配置数据库或持有者为空）
```

现阶段应把该问题定性为**首个真实候选断点：战术卡资源配置已存在，但奖励广播可能早于 TacticalCardPresenter 完成初始化**。需要通过一次启动日志确认：

```text
GameFlowManager.Initialize
TacticalCardPresenter.Initialize
ExplorationRewardSystem.OnBroadcast(Explored)
```

如果 `OnBroadcast(Explored)` 早于 `TacticalCardPresenter.Initialize()`，断点就在生命周期时序，而不是 Excel 配置。

### 3.4 断点 D：建筑奖励需要区分“预生成建筑为空”和“合法性/生成失败”

当前建筑结算：

```text
ExplorationRewardSystem.SettleBuilding()
  -> acquisition.BuildingConfig == null ? fallbackGold
  -> RewardBuildingRule.CanPlace(cell) ? 继续 : fallbackGold
  -> _buildingSpawnService.SpawnPlayerBuilding(...)
  -> false ? fallbackGold : Building
```

对应代码：`Assets/Scripts/Core/Services/Exploration/ExplorationRewardSystem.cs` 125-161 行。

当前日志使用的是：

```text
建筑奖励但 rewardBuildings 为空，降级为金币
```

但现在生产代码已经走 Excel Provider，`rewardBuildings` 是旧 SO 字段名称。这条日志不能直接证明 Excel 奖励池为空，只能证明传入 `acquisition.BuildingConfig` 为 null。

必须按以下顺序确认断点：

1. `MapGenerator.GenerateExplorationRewards()` 中生成 Building 后打印 `BuildingConfig != null`、`buildingId`；
2. `ExplorationAcquisition.Explored()` 中打印 `reward.BuildingConfig` 是否被复制；
3. `ExplorationRewardSystem.SettleBuilding()` 进入时打印 `acquisition.BuildingConfig` 和 `buildingId`；
4. 若配置非空，再打印 `RewardBuildingRule.CanPlace()` 的具体失败原因；
5. 若规则通过，再进入 `CardPresenter.SpawnBuilding()`，分别记录：
   - `h` 是否为空；
   - `GetBuildingPrefab(6)` 是否为空；
   - `PlayerBuilding` parent 是否为空；
   - `hasBuildingUi` 是否失败；
   - 最终是否写入 `h.BulidingTypeOnHex_Building`。

当前不能把“金矿允许作为奖励”改判为配置错误。真正的建筑断点尚未在这五个节点中锁定；旧日志文案属于误导信息，必须先换成新架构字段后再判断。

### 3.5 断点 E：单位日志文案与新架构不一致，不能据此认定单位池为空

`ExplorationRewardSystem.SpawnUnitsWithOverflow()` 198 行仍输出：

```text
探索奖励无可用单位配置（rewardUnits 为空）
```

但当前 `ExplorationRewardProvider` 不再读取 `ExplorationRewardConfigSO.rewardUnits`，而是读取 Excel 奖励池。因此该日志存在架构迁移后的旧文案残留。

必须先把诊断点改成：

```text
奖励快照 UnitConfigs.Count
UnitConfigs[i] 是否为空
UnitConfig.Id
SpawnPlayerUnit 返回值
```

在修改日志前，不能根据“rewardUnits 为空”断言 Excel 单位池为空。当前已知 Excel、UnitBalanceDatabase 和 UnitDatabase 均包含弓兵/剑客映射。

## 4. 按现有设计的修复计划

### 阶段 0：只做断点观测，不改玩法

优先增加 Development Build 诊断，不修改权重、不修改 0 档、不移除金矿：

1. `MapGenerator.GenerateExplorationRewards()`：输出每类预生成数量，以及 Building/Unit/Card 的具体 ID。
2. `ExplorationAcquisition.Explored()`：输出从快照复制到广播载荷的字段。
3. `ExplorationRewardSystem.Settle()`：输出原始类型、快照字段、实际结算入口。
4. `TacticalCardPresenter.Initialize()` 与 `AddCardWithFly()`：输出初始化时间、`_cardPrefab`、锚点、`_cardViews` 状态。
5. `CardPresenter.SpawnUnit/SpawnBuilding()`：输出资源、Prefab、Canvas 校验和返回值。

目标是得到一条带序号的单次探索链路，而不是继续依赖旧日志。

### 阶段 1：只修断点，不改配置设计

根据阶段 0 的结果分别处理：

- 若战术卡确实早于 Presenter 初始化：调整 `GameInstaller` 的 `BindInitializableExecutionOrder`，让 `TacticalCardPresenter.Initialize()` 先于 `GameFlowManager.Initialize()` 完成；或在奖励发放前建立待发队列。
- 若 BuildingConfig 在 Provider 已生成但 Acquisition 丢失：修复快照复制/载荷构造。
- 若 BuildingConfig 在 Provider 就为空：检查 `RollPoolEntry → BuildingBalanceDatabaseSO → IBuildingDataProvider → BuildingDatabaseSO` 每一步，不修改奖励池内容。
- 若 `SpawnBuilding` 失败：记录确切校验节点；按现有设计保持失败降级金币。
- 若 UnitConfigs 正常但 SpawnPlayerUnit 返回 null：检查单位 Prefab/UI 层级，不修改单位奖励池。

### 阶段 2：修正误导性日志和结算表达

涉及：

- `Assets/Scripts/Core/Services/Exploration/ExplorationRewardSystem.cs`；
- `Assets/Scripts/AI/AIAutoExplorer.cs`；
- `Assets/Scripts/Core/Services/Exploration/ExplorationAcquisition.cs`。

修改目标：

- 将旧的 `rewardUnits/rewardBuildings` 文案改为 `UnitConfigs/BuildingConfig`；
- MilitaryUnit x0 显示为“军事奖励：空（配置允许 0）”，不显示成获得单位；
- 建筑降级日志记录 `buildingId`、地块坐标和失败原因；
- 保留 `OriginalRewardType` 与 `SettledRewardType` 的区分；
- 不把所有失败统一伪装成金币或 None。

### 阶段 3：补充契约测试，但不改现有配置

新增/扩展：

- `Assets/Tests/ExplorationRewardGenerationTests.cs`：验证 0 档可生成合法空军事奖励；
- `Assets/Tests/ExplorationRewardProviderTests.cs`：验证 Excel 奖励池中的弓兵、剑客、战术卡、金矿均能解析；
- `Assets/Tests/ExplorationRewardSettlementTests.cs`：验证 x0、单位生成、战术卡初始化时序、建筑三条降级路径；
- `Assets/Tests/RewardBuildingRuleTests.cs`：验证金矿奖励按现有 `CanPlace` 规则处理；
- `Assets/Tests/ExplorationInitializationOrderTests.cs`：验证 Presenter 初始化早于首个奖励广播。

## 5. 暂不修改的内容

在真正断点锁定前，禁止：

1. 把 `unitCountTiers` 改成全正数；
2. 删除或替换 `building.gold_mine`；
3. 修改金矿地貌 `blockBuildingSpawn`；
4. 修改奖励权重；
5. 修改探索费用；
6. 删除旧 `ExplorationRewardConfigSO` 字段；
7. 重写奖励随机逻辑；
8. 把所有非金币奖励统一改成金币。

这些都属于玩法或数据语义变更，不能作为断点定位的替代方案。

## 6. 当前阶段结论

已经确认：

- Excel 奖励配置写全且已同步生成；
- 奖励类型掷点不是金币独占；
- 军事 x0 符合当前设计的空奖励语义；
- 基础 +5 Gold 来自独立的资源收割链路；
- 单位、战术卡、金矿资源 ID 映射在静态配置层存在；
- 现有日志中的 `rewardUnits/rewardBuildings` 是旧字段文案，不能作为新 Provider 断点证据。

当前最优先验证的真实断点：

1. **战术卡：首次探索奖励是否早于 `TacticalCardPresenter.Initialize()`；**
2. **建筑：`BuildingConfig` 是在 Provider 生成时为空，还是在 `SpawnBuilding` 时失败；**
3. **单位：UnitConfigs 已生成但 `SpawnPlayerUnit` 是否因 Prefab/UI 校验返回 null。**

只有把这三个节点用同一次探索的链路日志串起来，才能进行真正的代码修复。现阶段不应先改 Excel，也不应先改奖励设计。
