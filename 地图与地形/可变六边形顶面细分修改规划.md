# 可变六边形顶面细分修改规划

## 0. 目标与约束

把当前“六边形 / 十八边形”二档实现演进为 `solidEdgeSegments: 1..6`，支持 6、12、18、24、30、36 环点。本轮只写规划，不修改运行时代码。

约束：

1. 当前 `EighteenGon`（18 边）的几何、河道、水体、山体、迷雾和碰撞行为必须可回归。
2. 生产代码不再依赖固定 `18 / 44 / 25 / 19 / 54` 及 solid 索引 `7..43`。
3. 相邻格、跨 Chunk、山体/普通地形、陆地/水体之间不得产生裂缝或 T 形断口。
4. 视觉横向细分与高度台阶细分保持为两个独立概念。
5. 全部消费者迁移完成前不开放新档位，避免“平地支持、河道/山体不支持”的半完成状态。

## 1. 现状审计

### 1.1 固定 44 点 solid 布局

`Assets/Scripts/Core/Services/MeshDataGenerator.cs::ComputeSolidAreaVertices` 使用固定布局：

```text
0       中心
1..6    六个逻辑角点
7..18   每边两个内部点，共 12 点
19..24  河道表面内圈六点
25      河底中心
26..31  河底内圈六点
32..43  7..18 的河底副本，共 12 点
```

18 环点顺时针扇序（非 1..18 顺序）：

```text
1, 7, 8, 2, 9, 10, 3, 11, 12, 4, 13, 14, 5, 15, 16, 6, 17, 18
```

当前 `Hexagon` 模式并没有把拓扑缩成 6 点：它仍保留 18 环点，只把每边两个内部点移到直边的 1/3、2/3 位置，从而避免布局变化。但这无法自然扩展到 24/30/36 环点。

## 2. 参数与术语设计

### 2.1 使用“每条逻辑边的段数”，不用多边形枚举

建议新增最终权威配置：

```text
solidEdgeSegments: 1..6
```

定义：一条逻辑六边形边被切成多少段。

```text
1 -> 6 环点
2 -> 12 环点
3 -> 18 环点（当前默认）
4 -> 24 环点
5 -> 30 环点
6 -> 36 环点
```

派生量：

```text
s = solidEdgeSegments
k = s - 1              每边内部点数
ringCount = 6 * s      顶面环点数
```

使用 `segments` 而非 `subdivision`，避免与现有高度台阶参数 `useHeightBasedSubdivision / maxStepSubdivision` 混淆。

### 2.2 现有枚举迁移

当前 `solidAreaTopology` 同时影响轮廓形状和（间接）旧模式语义：

```text
EighteenGon = s=3 + 内切圆采样的内部点（当前生产默认）
Hexagon     = s=3 + 直边线性插值的内部点（仍保留 18 环点、44 点 packed 拓扑）
```

因此不能把存量 `Hexagon` asset 静默等价迁移为 `solidEdgeSegments=1`：这会从 44 点/18 环点突变为 20 点/6 环点，并改变三角数量、法线、山体 fan、Collider 和缓存契约。

建议新增两个正交概念：

```text
solidEdgeSegments: 1..6
solidEdgeShape:    InscribedArc | StraightEdge
```

迁移规则：

1. 新增 `solidEdgeSegments`，当前生产配置先固定为 3，运行时仍锁 s=3。
2. 新增 `solidEdgeShape`，把旧 `EighteenGon` 映射为 `InscribedArc`，把旧 `Hexagon` 映射为 `StraightEdge`。
3. 完成所有模块迁移与 s=3 回归后，显式迁移 `MapGenerationConfig.asset`。
4. 旧 `solidAreaTopology` 不得直接改类型覆盖原序列化字段；应保留 `[Obsolete]` 兼容字段，或提供 Editor 一次性迁移。
5. Inspector 显示分段数 1(6 环点)~6(36 环点)和形状选项。
6. 零回归硬门只针对当前生产配置 `EighteenGon → s=3 + InscribedArc`。旧 `Hexagon` 到 `s=1` 只保证轮廓意图近似，不保证拓扑兼容。

## 3. 目标拓扑抽象

### 3.1 新增单一权威布局类

建议新增 `Assets/Scripts/Core/Models/HexSurfaceLayout.cs`，其中定义 `HexSurfaceLayout` 类，只描述拓扑与索引，不生成具体世界坐标。

建议 API（命名可微调）：

```csharp
public sealed class HexSurfaceLayout
{
    public int SegmentsPerEdge { get; }
    public int InteriorPointsPerEdge { get; }
    public int RingCount { get; }
    public int SolidVertexCount { get; }
    public int WaterVertexCount { get; }
    public int RiverWaterVertexCount { get; }

    public int CenterIndex { get; }
    public int CornerIndex(int corner);
    public int EdgeInteriorIndex(int direction, int interiorIndex);
    public IReadOnlyList<int> GetEdgeProfileIndices(int direction);
    public IReadOnlyList<int> GetMirroredNeighborEdgeProfileIndices(int direction);
    public IReadOnlyList<int> GetRingIndicesClockwise();

    public int RiverSurfaceCornerIndex(int direction);
    public int RiverBottomCenterIndex { get; }
    public int RiverBottomCornerIndex(int direction);
    public int RiverBottomEdgeIndex(int direction, int interiorIndex);

    public float EdgeParameterForInteriorPoint(int interiorIndex);
}
```

输入约定：`corner/direction = 0..5`，`interiorIndex = 0..k-1`。

### 3.2 packed array 兼容期动态偏移

设 `k = s - 1`：

```text
Center                         0
Corner(c)                      1 + c
EdgeInterior(d,j)              7 + d*k + j
RiverSurfaceCorner(d)          7 + 6*k + d
RiverBottomCenter              13 + 6*k
RiverBottomCorner(d)           14 + 6*k + d
RiverBottomEdge(d,j)           20 + 6*k + d*k + j
SolidVertexCount               20 + 12*k
WaterVertexCount               13 + 6*k
RiverWaterVertexCount          7 + 6*k
MountainFlatFanVertexCount     3 * RingCount = 18 + 18*k
```

当前 `k=2` 精确得到 solid=44、water=25、river=19、mountain flat fan=54。

### 3.3 布局必须随数据传递

`SolidAreaMeshData` 与 `CellBuildContext` 都增加 `Layout` 字段。缓存写入时校验：

```text
solid.Length == layout.SolidVertexCount
lake.Length  == layout.WaterVertexCount
```

不要让消费者各自从 config 重算布局，否则配置热改或缓存残留会造成布局不一致。

### 3.4 消除三份方向→索引映射

当前相同映射分别维护于：

- `MeshDataGenerator`
- `ChunkMapRenderer.GetGenericRectangleMesh`
- `MountainGeometryBuilder.BuildMountainRectData`

全部统一改为：

```text
layout.GetEdgeProfileIndices(direction)
layout.GetMirroredNeighborEdgeProfileIndices(direction)
```

本格 profile 顺序：起始角点 → 内部点 → 终止角点。邻格 API 返回的 profile 已反转为与本格同下标对应。必须区分：

```text
selfProfile[p] <-> mirroredNeighborProfile[p]
selfProfile[p] <-> rawOppositeProfile[profileCount - 1 - p]
```

旧 `MeshDataGenerator.BuildRectVertices/BuildRectStepVertices` 不是上述两个 profile 的简单拼接，而是为旧 UV/draw-order 服务的交错顶点数组；这些活跃河道路径必须先抽取顶点角色模型，再程序化生成 vertices/UV/indices，不能机械替换索引后沿用旧 draw-order。

## 4. 顶点位置生成规则

### 4.1 角点与圆滑内部点

六个逻辑角点保持当前定义，半径 `OuterRadius * SolidAreaRatio`。

逻辑边 d 的第 j 个内部点先计算：

```text
t = (j + 1) / s
```

再按 `solidEdgeShape` 生成：

```text
StraightEdge：  Lerp(CornerA, CornerB, t)
InscribedArc：  按当前 s=3 的内切圆角度序列推广到动态 s，半径 = InnerRadius * SolidAreaRatio
```

必须先用 `s=3 + InscribedArc` 与当前 7..18 逐点对比，锁定角度、方向、索引镜像，以及由点 7 推导的河道内圈 `ratio`。`s=3 + StraightEdge` 则与当前旧 `Hexagon` 的 1/3、2/3 直边点逐点对比。

s=1 无内部点，直接生成真实 6 点环；此时形状选项不影响外轮廓。

### 4.2 扰动顺序

保持当前规则：先计算无扰动拓扑点，再调用 `HexMetrics.Perturb / PerturbY2`。由于 `SolidAreaRatio < 1`，相邻格的两个 solid profile 之间故意保留过渡带，世界坐标本来就不重合；要求的是索引/参数镜像正确，并由 rectangle transition 的起点连接本格 profile、终点连接邻格 mirrored profile。单测锁定扰动后的 transition 端点契约，而不是断言两侧 solid 坐标相等。

## 5. 河道专项设计

### 5.1 河岸锚点问题

当前河口和河岸固定使用 `t=1/3` 与 `t=2/3`。这些参数只在 s=3（18 边）和 s=6（36 边）天然成为视觉环顶点；s=1/2/4/5 不天然对齐。取第一/最后一个内部点或最近点吸附都会使河宽随档位变化。

### 5.2 推荐方案：河岸使用语义采样

新增：

```csharp
Vector3 SampleEdge(Vector3[] solid, HexSurfaceLayout layout, int direction, float t);
```

规则：

1. 从该边完整视觉 profile（角点 + 内部点 + 角点）中定位 t 所属小段。
2. 在相邻两个视觉点之间线性插值。
3. 河岸始终使用 `t=1/3, 2/3`，河宽与细分档位无关。
4. 河道局部网格把采样点作为显式顶点，不要求一定复用 solid 环索引。

优先验证策略 A：河道局部三角化插入采样点（点严格落在已有边段上），专项检查法线与 MeshCollider T 接点。若失败，升级策略 B：有河共享边 profile 采用视觉参数集合与 `{1/3, 2/3}` 的并集。策略 B 更严格，但缓存布局会依赖河流方向，复杂度更高。

### 5.3 河床逐步从 packed solid 解耦

建议新增 `RiverBedProfileData`：

```text
CenterBottom
SurfaceInnerCorners[6]
BottomInnerCorners[6]
BottomEdgeProfiles[6]   // 每条边动态长度
```

迁移顺序：

1. 先用 layout 动态偏移复刻当前 packed 数据。
2. s=3 回归通过后，让 `BuildRiverVertices` 与河道 draw order 读取结构化河床。
3. 最后决定是否从 `SolidAreaMeshData.Vertices` 移除河道块。

不要在第一步同时改变数组布局和河道三角算法，否则回归定位困难。

### 5.4 河道三角程序化

按语义重写，不再维护数字索引表：

- 无河道：完整中心扇。
- 河源/河尾：一个方向开口，其余环面保留。
- 中流相邻：两个开口 + 中央连接。
- 相差 2：两个开口 + 中间一条边对应的河底/侧壁。
- 贯穿：两个相对开口，按两侧多边形分别三角化。

河水 UV 直接按顶点角色写入，不再从 draw-order 的 `l[n]` 反推角色。

方向测试覆盖：河源/河尾 6 方向；中流相邻 12 有向组合；相差 2 的 12 有向组合；贯穿 6 有向组合（或按对称性归并），全部乘以 s=1..6。

## 6. 按阶段实施规划

### 阶段 2：顶面坐标、UV、普通 draw order 循环化

修改 `MeshDataGenerator.cs`：

- 循环生成角点、内部点和 packed block，并按 `solidEdgeShape` 选择内切圆采样或直边插值。
- UV 按环参数生成。
- `GetPlaneFace / BuildSolidAreaDrawOrder1` 改为程序化中心扇。
- 删除 12 个固定 `π*n/18` 角度字面量。
- 在重写 `ratio` 前继续使用与现状数值等价的公式；逐点比较完整 packed 44 点，尤其是河道块 `19..43`，不能只比较顶面 `0..18`。

退出条件：`s=3 + InscribedArc` 的完整顶点、UV 和索引逐项一致；`s=3 + StraightEdge` 与旧 Hexagon 的 `0..18` 轮廓逐点一致。

### 阶段 3：矩形与三角过渡 profile 数量泛化

修改 `ChunkMapRenderer.cs`、`TriangleTransitionMesh.cs`：

- `GetGenericRectangleMesh` 通过 layout 取得整边 profile。
- `RectangleTransitionMesh.Build` 接受任意 `profileCount >= 2`。
- strip 数改为 `profileCount - 1`；UV 横向分母同步变化。
- `RectangleDrivenTriangleMesh` 使用首/末 profile，不再用固定索引 3。
- 高度台阶 profile 与横向 profile 保持两个独立维度。
- 本阶段泛化的是通用非河 rectangle/triangle。运行时有河边仍调用 `MeshDataGenerator.BuildRectVertices/BuildRectStepVertices` 等旧路径，必须继续锁 `s=3`，并在阶段 6 按显式顶点角色模型统一迁移；不得把这些 `BuildRect*` 误判为死代码。

退出条件：通用非河路径在 s=1..6 的同高、坡、台阶跨格 profile 和三角角落无裂缝、无退化面；全局配置仍不开放，因此河道路径继续以 s=3 回归。

### 阶段 4：山体环扇与山体过渡泛化

修改 `MountainGeometryBuilder.cs`、`ChunkMapRenderer.cs`、Mountain Tests 与性能工具：

- 删除固定 `RingFanOrder`，使用 layout 环序。
- `EdgePointLift` 用 layout 取得 edge 与参数 t，再 `Lerp(cornerA, cornerB, t)`。
- 连续脊线边第一版保持所有内部点取 pair mean；山-非山边保持当前 `BoundaryEdgeRatio` 语义。
- `BuildSolidMountain` 使用动态 RingCount。
- 山体预算改为 `3 * layout.RingCount`，不保留全局 54 常量。
- `BuildMountainRectData / BuildRectFromProfiles` 泛化 profile 数；三角 profile 用首/末语义访问。

退出条件：s=3 数值回归；s=1..6 镜像山边一致、无退化面、跨 Chunk 无裂缝。

### 阶段 5：湖海与海岸泛化

修改 `MeshDataGenerator.cs`、`CellMeshData.cs`、`IMeshGenerator.cs`：

- 不再复制固定前 25 点；按 layout 获取中心、完整环和六个表面内圈点。
- 水面顶点数、UV、draw order 程序化。
- 水体矩形/海岸矩形使用完整动态边 profile；`BuildCoastRectUV/DrawOrder` 接受动态 profile 数。
- 海岸三角端点来自动态矩形 profile。

退出条件：s=1..6 水面、海岸、水-陆/水-山共享边无裂缝。

### 阶段 6：河床、地表河槽和河水泛化

修改 `MeshDataGenerator.cs`、`IMeshGenerator.cs`、`CellMeshData.cs`、`ChunkMapRenderer.cs`：

- 引入语义河岸采样 `t=1/3, 2/3`。
- 河道内圈比例改成命名配置/常量或明确公式，不再依赖点 7；切换前先证明 s=3 与阶段 0 记录的 `ratio` 和 `19..43` 完全一致。
- 先动态偏移复刻 packed block，再逐步解耦 `RiverBedProfileData`。
- 程序化生成河道地表、河底、侧壁、河水与下游过渡；覆盖全部河流方向组合。
- 迁移仍在运行的河道 rectangle 路径：`BuildRectVertices`、`BuildRectUV`、`BuildRectDrawOrder`、`BuildRectSlopeRiverDrawOrder`、`BuildRectStepVertices`、`BuildRectStepUV`、`BuildRectStepDrawOrder`、`BuildRectStepRiverDrawOrder`。
- 旧河道 rect 的交错数组先拆为明确角色（两侧 surface profile、河口、河底和侧壁点），再由角色程序化生成 vertices/UV/indices；禁止只替换固定索引而保留旧 draw-order。

退出条件：s=3 与现状一致；s=1..6 河宽一致、河道 rectangle/step 全部闭合、无空洞，MeshCollider 无非流形/退化警告。

### 阶段 7：迷雾、地图真实轮廓和边界语义清理

明确三类边界：

1. 视觉真实轮廓：`AddOpenEdgePoints`、`BuildMapRealOutline`、迷雾 connector 内边，使用完整动态 visual profile。
2. 逻辑六边形边界：势力范围、城墙/城墩占格边、探索拓扑追踪、`HexHighlightRenderer`，继续使用六角点，除非产品另有决定。
3. 完整逻辑地块足迹：`ChunkMapRenderer.BuildChunkGrid` 与 `StampCellToFogMask` 继续使用 `OuterRadius/InnerRadius`，不使用缩小后的 `SolidAreaRatio`，默认不随 `solidEdgeSegments` 或 `solidEdgeShape` 改变。

API 命名加入 `LogicalHex / LogicalFootprint / VisualSurface` 区分；检查动态视觉轮廓去重、顺序、闭环和 winding。不同 s 下，相同 FogAlpha 状态的 `_FogMaskTex` 应保持一致。

### 阶段 8：接口、注释、缓存和旧代码清理

- 删除“44/25/19 点”固定接口文档。
- 所有数组访问通过 layout 或结构化数据。
- 搜索清理：`[7]..[43]`、`new Vector3[44/25]`、`SolidMountainFanVertexCount=54`、`RingFanOrder`、边点 `/2,%2`、`Profiles[3]`、`starts.Count!=4`。
- `BuildTri*` 与 `BuildRect*` 必须分别做运行时调用审计：当前部分旧 `BuildRect*` 是活跃河道路径，只有在阶段 6 完成替代且调用点为零后才能删除；不得因名称相近与死代码 `BuildTri*` 一并清理。
- 清理或更新 `HexHighlightRenderer`、接口注释、测试夹具和性能工具中的固定布局描述。

退出条件：生产代码不再包含固定 18 环布局魔法索引。

### 阶段 9：配置迁移与 Inspector 开放

- 正式启用 `solidEdgeSegments` 与 `solidEdgeShape`。
- 当前 asset 从 `EighteenGon` 显式迁移为 `solidEdgeSegments=3 + solidEdgeShape=InscribedArc`。
- 存量 `Hexagon` 显式迁移为 `solidEdgeSegments=3 + solidEdgeShape=StraightEdge`，不得静默迁移为 s=1。
- 移除或废弃 `solidAreaTopology`，迁移工具需可重复运行并输出变更报告。
- Inspector 显示分段数 1(6 环点)~6(36 环点)及轮廓形状；s=1 时说明形状选项对内部点无影响。
- 第一版只保证完整地图/Chunk 重建后生效，不承诺运行时即时热切换。

### 阶段 10：性能与完整验收

- 每档记录 Chunk 构建耗时、顶点/三角形、collision Mesh 提交次数、动画 UV2/UV3 成本、GC；若需要 PhysX cooking 时间，另用 Profiler 采样，不把 `CollisionCommitCount` 当作内部 cooking 次数。
- 固定地图规模与 seed，对比 s=3 基线。
- 高档位超预算时限制 Inspector 最大值，不允许不同 Chunk/地块采用不同 s。

## 7. 测试矩阵

- 布局：s=1..6 的 count、索引范围、环序、每边 profileCount=s+1、邻格镜像。
- 顶面：s=3 逐点回归；s=1 真实六点环；三角数=RingCount；winding/UV 正确。
- 过渡：s=1..6 × 同高/坡/单级/多级台阶 × NE/E/SE × 普通/山体组合。
- 河道：全部河型和有向组合 × s=1..6；河宽恒定、河水不穿地、下游闭合。
- 水体：水-水、水-陆、水-山、跨 Chunk。
- 山体：预算 `3*RingCount`；共享角、连续脊边、镜像、山-非山回落、UV0、动画来源。
- 迷雾：视觉外轮廓随 s 变化且闭合无自交；逻辑势力/城墙拓扑不变。
- 集成截图：平地、河源/转弯/贯穿、海岸、山边、多级台阶、迷雾、Chunk 接缝、动态高度动画。

## 8. 性能预估

```text
s   ring   solid   water   riverWater   mountainFlatFan
1     6      20      13        7             18
2    12      32      19       13             36
3    18      44      25       19             54
4    24      56      31       25             72
5    30      68      37       31             90
6    36      80      43       37            108
```

s=3 到 s=6：solid 44→80（约 1.82 倍）；山体 flat 顶点 54→108（2 倍）；矩形横向 strip 3→6（2 倍）；碰撞、动画 UV2/UV3、权重与动画来源数组同步增长。

性能门槛：s=3 构建耗时增幅目标不超过 5%（以现有 `MountainPerformanceBaseline` 工具实测）；s=6 超预算则限制最大档，不允许局部降级造成共享边失配。

## 10. 明确不采用的捷径

1. 继续增加 `TwentyFourGon/ThirtyGon/ThirtySixGon` 枚举并手写坐标：只解决顶点位置，不解决下游索引。
2. 固定 36 点并让多余点重合：制造退化三角、法线和 Collider 风险。
3. 只改平地，河道/山体保持 18 点：共享 profile 数不同，产生裂缝/T 接点。
4. 河岸吸附最近环点：12/24/30 档河宽不一致。
5. 复用 `maxStepSubdivision`：横向轮廓与高度台阶含义、生命周期不同。
6. 同时重排 packed solid、重写河道并开放配置：回归变量过多，必须按阶段以 s=3 为兼容门。

## 11. 完成定义

1. `MapGenerationConfig.asset` 只改 `solidEdgeSegments` 即可选择六档。
2. 新增档位无需修改顶点数组或 draw-order 源码。
3. 生产代码不再依赖固定 18/44/25/19/54 数字。
4. s=3 固定 seed 地图与迁移前几何/截图一致，或差异经过明确批准。
5. 六档均通过普通地形、台阶、河道、水体、山体、迷雾、Chunk 接缝和碰撞测试。
6. 河宽、海岸、水位、山体共享边高度不随 s 发生非预期变化。
7. 性能报告包含六档数据，并为 Inspector 最大值提供依据。
