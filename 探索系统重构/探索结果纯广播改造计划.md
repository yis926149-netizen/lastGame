# 探索结果纯广播改造计划

> 目标：探索成功后，把“探索获得了什么、最终实际发放了什么、当前处于哪个时机”通过一条统一广播流对外通知。探索服务只负责探索事务与阶段推进；奖励结算、AI、动画、金币表现和 UI 各自订阅、过滤并执行逻辑。
>
> 状态：设计已按现有代码复核并修订，待实施。本文档只描述改动方案，不包含实际代码修改。

---

## 1. 背景与目标

### 1.1 当前事实

- 每个地块在地图生成时已经固化 `ExplorationRewardData` 奖励快照。
- 探索费用会在探索前读取 `cell.ExplorationReward.RewardType`，因此奖励快照必须保留到费用校验和扣费完成之后。
- `HexCellData.TakeExplorationReward()` 会取出并清空奖励快照，只能消费一次。
- 建筑奖励包含备用 `GoldAmount`；建筑配置缺失、地块不合格或生成失败时，会实际降级为金币。
- 玩家有探索动画和动画奖励点；AI 没有玩家视角动画，也没有 `RewardPoint`。

### 1.2 改造目标

1. 用一条统一广播流取代 `CellExplored`、`ExplorationRewardTriggered` 和 `ExplorationPillarPool.ExplorationRewardPoint`。
2. 奖励快照只允许 `ExplorationService` 调用一次 `TakeExplorationReward()`。
3. 区分“原始奖励”和“实际结算结果”，正确覆盖建筑降级金币。
4. 载荷携带地块、阵营、阶段、原始奖励、实际奖励及对应数据。
5. 每个订阅者独立过滤和执行；单个订阅者异常不能阻断其他订阅者。
6. 玩家动画异常或中断时不能永久遗留待处理载荷，也不能永久丢失金币表现。

## 2. 现状与问题

### 2.1 当前事件面

| 事件 | 触发点 | 载荷 | 当前订阅者 |
|---|---|---|---|
| `IExplorationService.CellExplored` | 玩家探索成功 | cell | `ExplorationPillarPool`、`CostLabelRenderer` |
| `IExplorationService.ExplorationRewardTriggered` | 玩家或 AI 探索成功 | cell + factionId | `ExplorationRewardSystem`、`AIAutoExplorer` |
| `ExplorationPillarPool.ExplorationRewardPoint` | 石柱溶解 30% / 飞盘撞击 | cell | `ExplorationCoinPresenter` |

### 2.2 核心问题

1. 奖励类型和奖励数据没有进入事件载荷，接收者只能反查并消费 cell。
2. 多个接收者调用 `TakeExplorationReward()` 会发生第二次取到 `null` 的问题。
3. 原始奖励类型不等于实际结算类型。建筑奖励可能实际降级为金币。
4. 直接调用 C# 多播事件时，一个订阅者抛异常会阻断后续订阅者。
5. 当前金币表现依赖 `_pendingCoins` 做“结算登记 -> 动画触发”桥接。
6. 当前 `_pendingCompletions` 只删除标记，没有对动画失败或中断进行兜底。
7. `ExplorationRewardSystem` 用 finalizer 解绑事件，`AIAutoExplorer` 完全没有解绑，生命周期不可靠。

## 3. 修订后的设计决策

### 3.1 一条统一广播流

新增统一广播中心 `ExplorationBroadcastHub`：

```csharp
public interface IExplorationBroadcastSource
{
    event Action<ExplorationAcquisition> Broadcast;
}

public interface IExplorationBroadcastPublisher
{
    void Publish(ExplorationAcquisition acquisition);
}
```

`ExplorationBroadcastHub` 同时实现两个接口：

- 普通接收者只注入 `IExplorationBroadcastSource`，只能订阅。
- `ExplorationService`、`ExplorationRewardSystem`、`AIAutoExplorer` 注入 `IExplorationBroadcastPublisher`，可以发布后续阶段。
- 全项目只有一个 `Broadcast` 事件，不再在 `IExplorationService` 和表现组件上保留其他探索结果事件。

不把 `Publish` 暴露给所有接收者，避免普通表现层随意伪造领域消息。

### 3.2 三个广播阶段

```csharp
public enum ExplorationBroadcastPhase
{
    /// <summary>探索事务成功，原始奖励快照已经由服务唯一物化。</summary>
    Explored,

    /// <summary>玩家或 AI 奖励处理器完成实际结算。</summary>
    Settled,

    /// <summary>玩家探索动画到达奖励表现点，或动画异常时执行兜底。</summary>
    RewardPoint,
}
```

阶段规则：

- 玩家：`Explored -> Settled -> RewardPoint`。
- AI：`Explored -> Settled`，不产生 `RewardPoint`。
- `Settled` 必须表达实际发放结果，不能只复制原始奖励类型。
- `RewardPoint` 复用 `Settled` 结果，金币表现按实际奖励类型判断。

### 3.3 原始奖励与实际奖励分离

载荷必须同时包含：

- `OriginalRewardType`：地图生成时固化的类型。
- `SettledRewardType`：最终实际发放的类型。
- `OriginalGoldAmount`：原始快照中的金币值，包括建筑的备用金币。
- `SettledGoldAmount`：最终实际发放的金币数量。

示例：

| 场景 | OriginalRewardType | SettledRewardType | SettledGoldAmount |
|---|---|---|---|
| 普通金币奖励 | Gold | Gold | 原金币数量 |
| 建筑成功生成 | Building | Building | 0 |
| 建筑不可放置，降级金币 | Building | Gold | 备用金币数量 |
| 无奖励 | None | None | 0 |

这样 `ExplorationCoinPresenter` 只需过滤 `RewardPoint + SettledRewardType == Gold`，不会漏播降级金币，也不会在建筑成功时误播金币。

### 3.4 奖励快照唯一消费

`TryExplore` 的顺序必须是：

1. 校验目标格。
2. 读取奖励类型并计算费用。
3. 扣费。
4. 标记探索、取得归属、重算后勤、收割资源。
5. 调用一次 `targetCell.TakeExplorationReward()` 并构造 `Explored` 载荷。
6. 建立玩家侧待处理记录。
7. 触发地图视觉事件和统一探索广播。

第 5 步必须发生在 `_mapVisualEvent.Raise()` 和任何探索广播之前，确保外部监听器无法抢先消费奖励快照。

### 3.5 缺失快照不能伪装成 None

`reward == null` 和显式 `RewardType.None` 语义不同：

- `None` 是合法的“本格无奖励”。
- `null` 表示地图奖励预生成或数据生命周期异常。

载荷增加 `HasRewardSnapshot`。服务遇到 `null` 时：

- 记录 `Debug.LogError`，包含 cell 坐标和 factionId。
- 仍发布 `Explored`，避免探索事务已经提交后 UI/动画完全失去通知。
- 结算者看到 `HasRewardSnapshot == false` 时只发布 `Settled(None)`，不发放奖励。

### 3.6 广播必须排队并隔离异常

`ExplorationBroadcastHub.Publish()` 不应直接执行 `Broadcast?.Invoke(...)`，而应满足：

1. 使用内部 FIFO 队列，避免 `Explored` 处理器发布 `Settled` 时发生重入，保证当前消息先通知完所有订阅者。
2. 对 invocation list 中每个订阅者单独 `try/catch`。
3. 一个订阅者失败时记录异常并继续通知其他订阅者。
4. 队列处理使用 `_isDispatching` 防止嵌套递归。

阶段消息的全局可观察顺序因此稳定为：

```text
Explored 通知全部订阅者
Settled 通知全部订阅者
RewardPoint 通知全部订阅者
```

### 3.7 浅只读资源引用 + 不可修改集合

载荷属性全部只读。`ScriptableObject` 配置资源按引用传递，不做深复制；`UnitConfigs` 在构造时复制数组并通过 `IReadOnlyList<UnitConfigSO>` 暴露，防止一个订阅者修改集合影响其他订阅者。

因此准确语义是：

- 载荷对象不可变。
- 集合结构不可由接收者修改。
- SO 资源本身仍是共享只读配置引用，接收者不得修改资源内容。

## 5. 接收者自治规则

| 接收者 | 过滤条件 | 行为 |
|---|---|---|
| `ExplorationPillarPool` | `Explored && FactionId == 0` | 播放石柱或飞盘动画 |
| `ExplorationRewardSystem` | `Explored && FactionId == 0` | 结算玩家奖励并发布 `Settled` |
| `AIAutoExplorer` | `Explored && FactionId == AIIndex` | 结算 AI 奖励并发布 `Settled` |
| `ExplorationService` | `Settled && FactionId == 0` | 缓存玩家实际结算结果，供动画奖励点复用 |
| `ExplorationCoinPresenter` | `RewardPoint && FactionId == 0 && SettledRewardType == Gold` | 使用 `SettledGoldAmount` 播放金币表现 |
| `CostLabelRenderer` | 不再订阅探索广播 | 继续通过已有 `_mapVisualEvent` 请求刷新 |

`CostLabelRenderer` 已经订阅 `MapVisualEventSO.OnMapVisualChanged`，而 `TryExplore` 会调用 `_mapVisualEvent.Raise()`。继续订阅探索广播只会重复设置同一个 `_refreshRequested`，因此直接删除它对 `IExplorationService.CellExplored` 的订阅即可。

## 6. 按文件修改清单

### 6.1 新增文件

| 文件 | 内容 |
|---|---|
| `ExplorationAcquisition.cs` | 三阶段枚举和不可变载荷 |
| `ExplorationBroadcastHub.cs` | 单一排队广播流、异常隔离、源/发布接口 |

### 6.2 `IExplorationService.cs`

- 删除 `CellExplored`。
- 删除 `ExplorationRewardTriggered`。
- 保留 `TryExplore`。
- 将 `CompleteExploration` 更名为 `SignalRewardPoint`，准确表达“动画到达奖励点”。
- 若暂不更名，至少更新注释，不再声称该方法执行领土、收割和视觉刷新。

建议接口：

```csharp
ExploreResult TryExplore(HexCellData targetCell, int factionId);
void SignalRewardPoint(HexCellData targetCell);
```

### 6.3 `ExplorationService.cs`

- 注入 `IExplorationBroadcastSource` 和 `IExplorationBroadcastPublisher`。
- 订阅 `Settled` 阶段，用于接收玩家实际结算结果。
- `_pendingCompletions` 改为玩家侧 pending 字典，记录：
  - `Explored` 载荷；
  - `Settled` 载荷；
  - 建立时间；
  - 是否已经发出 `RewardPoint`。
- `TryExplore` 在任何外部事件前唯一调用 `TakeExplorationReward()`。
- `SignalRewardPoint` 必须幂等：只有第一次成功移除 pending 并发布 `RewardPoint`。
- `SignalRewardPoint(null)` 直接返回并记录警告，不调用字典 API。
- 实现 `IDisposable`，解绑广播订阅。

玩家 pending 在 `Explored` 前建立，防止同步广播过程中发生状态遗漏。`Settled` 到达后更新同一记录；正常动画延迟远大于同步结算，因此奖励点会读取到实际结算结果。

若奖励点在 `Settled` 前异常提前到达，不立即发布错误的原始结果，而是标记 `RewardPointRequested`；待 `Settled` 到达后再发布。

### 6.4 动画失败和 pending 兜底

服务增加 pending 超时检查，推荐 10 秒：

- 正常动画调用 `SignalRewardPoint` 后立即移除。
- 动画中断、对象禁用或材质缺失导致回调不发生时，超时后使用已缓存的 `Settled` 结果发布一次兜底 `RewardPoint` 并移除。
- 若超时时 `Settled` 仍缺失，记录错误并移除，不能永久持有 cell 和奖励资源。

为了让 Zenject 驱动超时检查：

```csharp
Container.BindInterfacesAndSelfTo<ExplorationService>().AsSingle();
```

`ExplorationService` 实现 `IExplorationService`、`ITickable` 和 `IDisposable`，上述单条绑定会让这些接口和具体类型解析到同一个单例。不要再额外执行 `Bind<IExplorationService>().To<ExplorationService>()`，避免产生重复绑定或生命周期不一致。如果项目希望避免服务依赖 Unity 时间，可改为独立 `ExplorationRewardPointCoordinator : ITickable`，但不得删除超时兜底。

### 6.5 `ExplorationRewardSystem.cs`

- 订阅统一广播源，只处理玩家 `Explored`。
- 删除 `cell.TakeExplorationReward()`。
- 从载荷读取原始奖励字段。
- 每条处理路径结束后发布且只发布一个 `Settled`：
  - Gold 成功：`SettledAs(Gold, amount)`。
  - Building 成功：`SettledAs(Building)`。
  - Building 降级：`SettledAs(Gold, fallbackAmount)`。
  - MilitaryUnit：`SettledAs(MilitaryUnit)`。
  - TacticalCard：按当前实际规则发布 TacticalCard；配置缺失时仍记录警告。
  - None 或缺失快照：`SettledAs(None)`。
- `AddGoldReward` 只负责钱包入账，不再调用 presenter。
- 删除 `_coinPresenter` 字段和构造参数。
- 实现 `IDisposable`，删除 finalizer。

结算内部发生异常时，应在记录异常后发布 `SettledAs(None)` 或明确的失败结果，避免玩家 pending 永久等待。若未来需要区分失败，新增 `SettlementSucceeded` 和错误码，不要复用奖励类型表示失败。

### 6.6 `AIAutoExplorer.cs`

## 7. 修订后时序

### 7.1 玩家普通金币奖励

```text
TryExplore(cell, 0)
  -> 校验、扣费、探索、归属、后勤、资源收割
  -> reward = cell.TakeExplorationReward()       // 唯一消费
  -> pending[cell] = Explored acquisition
  -> mapVisualEvent.Raise()
  -> Publish(Explored)
       -> PillarPool 播放动画
       -> RewardSystem 金币入账并 Publish(Settled: Gold, amount)
  -> Hub 在 Explored 全部分发完成后分发 Settled
       -> ExplorationService 缓存实际结算结果
  -> 动画到达奖励点
       -> SignalRewardPoint(cell)
       -> Publish(RewardPoint: Gold, amount)
       -> CoinPresenter 播放金币表现
```

### 7.2 玩家建筑降级金币

```text
Publish(Explored: Original=Building, OriginalGoldAmount=fallback)
  -> RewardSystem 判断不可建造/生成失败
  -> 钱包增加 fallback
  -> Publish(Settled: Original=Building, Settled=Gold, SettledGoldAmount=fallback)
  -> Service 缓存 Settled
  -> RewardPoint 复用 Settled
  -> CoinPresenter 正确播放 fallback 金币表现
```

### 7.3 玩家建筑成功

```text
Publish(Explored: Original=Building)
  -> RewardSystem 成功生成建筑
  -> Publish(Settled: Settled=Building, SettledGoldAmount=0)
  -> RewardPoint
  -> CoinPresenter 因 SettledRewardType != Gold 忽略
```

### 7.4 AI 探索

```text
TryExplore(cell, AIIndex)
  -> 唯一消费快照
  -> Publish(Explored)
  -> AIAutoExplorer 结算并 Publish(Settled)
  -> 无玩家 pending、无动画、无 RewardPoint
```

## 9. 测试清单

### 9.1 广播中心

- 同一消息通知全部订阅者。
- 一个订阅者抛异常时，其他订阅者仍收到消息。
- 订阅者在处理 `Explored` 时发布 `Settled`，`Settled` 必须在所有 `Explored` 订阅者执行完后分发。
- FIFO 队列无递归重入和重复消息。

### 9.2 服务阶段状态机

- 玩家成功探索阶段顺序为 `Explored, Settled, RewardPoint`。
- 重复调用 `SignalRewardPoint` 不产生第二个 `RewardPoint`。
- `SignalRewardPoint(null)` 不抛异常。
- AI 只产生 `Explored, Settled`。
- 玩家动画超时后只兜底发布一次 `RewardPoint` 并清除 pending。
- 奖励点早于 `Settled` 时先等待，收到 `Settled` 后再发布。

### 9.3 奖励所有权与载荷

- `TryExplore` 后 `cell.ExplorationReward == null`。
- 载荷仍完整保留奖励字段。
- `TakeExplorationReward()` 在生产代码中只由 `ExplorationService` 调用。
- 显式 None 与缺失快照可以区分。
- 一个订阅者不能修改 `UnitConfigs` 并影响其他订阅者。

### 9.4 实际结算结果

- 普通 Gold：正确入账，RewardPoint 金额正确且只表现一次。

## 11. 风险与约束

1. **广播不是事务回滚机制**：探索事务提交后，表现层失败只记录并隔离，不能回滚扣费和归属。
2. **实际结算结果必须广播**：不得直接把原始 Building 载荷复制到 RewardPoint，否则会再次漏掉降级金币。
3. **禁止广播重入**：hub 必须排队；否则嵌套 `Settled` 会插入尚未完成的 `Explored` 分发中。
4. **阶段过滤必须严格**：奖励系统只处理 `Explored`，否则会因收到自身发布的 `Settled` 而递归结算。
5. **AI 无 RewardPoint**：只有玩家侧建立动画 pending。
6. **动画回调不可靠**：服务必须有超时清理和兜底广播。
7. **SO 引用按只读使用**：载荷不可变不代表 Unity `ScriptableObject` 本身不可变。
8. **解绑依赖 DI 生命周期**：新增 `IDisposable` 后必须确认绑定方式确实把接口注册到容器。
9. **地图视觉事件仍存在**：它负责通用地图刷新，不属于探索结果广播，不能与旧 `CellExplored` 混淆。
10. **性能**：每次探索固定产生少量阶段载荷；避免 `ToRewardData()` 中间对象，数组只在 `Explored` 构造时复制一次。对象池逻辑保持不变。

## 12. 最终架构边界

```text
ExplorationService
  负责：探索事务、奖励快照唯一物化、玩家 RewardPoint 状态机
  发布：Explored、RewardPoint

ExplorationRewardSystem / AIAutoExplorer
  负责：各阵营实际奖励结算
  订阅：Explored
  发布：Settled

ExplorationBroadcastHub
  负责：单一广播流、FIFO、异常隔离
  不负责：奖励规则、阵营规则、动画规则

ExplorationPillarPool / ExplorationCoinPresenter / UI
  负责：各自表现
  只订阅和过滤，不读取或消费 cell 上的奖励快照
```

该边界同时满足奖励唯一消费、接收者自治、建筑降级金币正确表现、AI/玩家隔离和动画时机对齐。
